# 性能优化实验台账

本文件是 `dev` 分支从 v2.0.0 演进到 v3.0.0 的追加式证据索引。策略定义、架构瓶颈、测试矩阵
和准入规则见[性能调优](性能调优.md)。未经目标 Linux/CUDA 实测的内容不得标记为“采纳”。

## 管理规则

- 实验 ID 使用 `PERF-<领域>-<三位序号>`，创建后不得复用；历史导入使用 `HIST-` 前缀。
- 状态只允许：`候选`、`就绪`、`测试中`、`采纳`、`拒绝`、`阻塞`。
- 一次只改变一个主要变量；多因素实验必须提前写明矩阵与交互假设。
- 每组至少预热 3 条、执行 3 轮，使用中位数决策，同时保留最差一轮。
- 拒绝和阻塞记录不删除；硬件、vLLM 或模型版本变化后可新建 ID 重新验证。
- 原始音频、模型、完整业务日志和敏感正文不进入 Git；提交去敏摘要、SHA256 和决策。
- 只有“采纳”且构成重要里程碑的提交创建带注释 tag，失败实验不打 tag。

## PERF-OBS-001：机器可读压测证据

- 状态：就绪
- 日期：2026-07-27
- 假设：统一 JSON 报告可消除终端文本抄录误差，并固定后续实验的环境、输入和指标证据。
- 实现：`tests/test_service.py` 新增 `--output-json`、`--metrics-url`、`--skip-metrics` 和
  `--require-server-timing`；采用同目录临时文件加 `os.replace` 原子写入严格 JSON。
- 报告：Git 提交/分支/已跟踪修改状态及未跟踪文件计数、Python/平台/关键包、性能环境白名单、
  健康响应、音频文件名/大小/SHA256/时长、测试参数、错误分类、吞吐/延迟、阶段分位数、资源
  摘要和 vLLM 指标前后快照；不记录音频内容、热词值、`article_url` 值或非白名单环境变量。
- 无 GPU 验证：Windows 本机使用 aiohttp 假 vLLM，native 接口预热 1 次、并发 2、正式 3 次；
  JSON `schema_version=1`、成功数 3、阶段覆盖率 100%，前后指标均解析成功。
- 门禁结论：实现 GO；性能采集开销尚未在目标 Linux/CUDA 校准，不能标记“采纳”。
- 下一步：在 `PERF-BASE-001` 每个条件保存三份独立报告，比较开启/关闭报告与指标采集的开销。

## PERF-OBS-002：网关阶段与排队耗时

- 状态：就绪
- 日期：2026-07-27
- 假设：统一的服务端阶段计时可以区分网关 CPU、分片排队、HTTP/vLLM 和 Aligner 瓶颈。
- 实现：完成日志 `stage_timings_ms` 与 `Server-Timing` 共用 14 个固定指标；分片本地/全局
  信号量记录累计与最大等待，`asr-backend` 记录分片 HTTP 累计，`asr`/`total` 记录墙钟；
  Aligner 返回独立 queue/inference 耗时，JSON 成功和错误响应统一测量序列化。
- 安全性：分片等待全局槽时若取消或异常，会释放已获得的本地槽；后端完成或失败后按获得状态
  释放两级信号量，不改变原有并发预算。
- 无 GPU 验证：假 vLLM 覆盖 `/chinese_asr` 和 multipart，响应 JSON/错误契约不变；14 个阶段
  均为有限非负数，压测器严格解析并实现 100% 覆盖门禁。
- 门禁结论：实现 GO；真实并发下计时开销、vLLM 指标相关性和 Aligner 排队仍待目标 GPU 验证。
- 回滚：移除响应头和细分计时但保留原请求总耗时；任何可测吞吐退化超过门禁时不得采纳。
