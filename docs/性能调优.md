# 性能调优与基准（v2.1.0）

## 1. 参数分层

不要混淆以下四种并发：

| 参数 | 当前默认值 | 含义 |
|---|---:|---|
| `VLLM_MAX_NUM_SEQS` | 128 | vLLM scheduler 最大活跃序列数，不是固定 batch |
| `CHUNK_CONCURRENCY` | 3 | 单个长音频最多同时提交的分片数 |
| `LONG_CHUNKS_IN_FLIGHT` | 96 | 全局长音频分片在途上限，短音频不占用 |
| 压测 `--concurrency` | 96 | 客户端同时发送的原始请求数 |

v1.0.0 发布时采用 `3/64`；v2.0.0 统一为 `3/96`、32 秒分片和 0～2000 秒输入。
下表历史 A10 数据显示纯 90 秒的 `3/96` 吞吐最高；默认同卡 ForcedAligner 和真实混合流量
仍须在发布前复测。

## 2. 已有 A10 实测

测试条件：单张 A10、90 秒音频、2000 请求、客户端并发 96、每条切为 3 片、
`CHUNK_CONCURRENCY=3`。数据来自实际测试记录，未在本次 Windows 文档整理中重跑。

| LONG_CHUNKS_IN_FLIGHT | audio_s/s | 平均延迟 | P95 | P99 | 结论 |
|---:|---:|---:|---:|---:|---|
| 32 | 1136.31 | 7434.6 ms | 7512.1 ms | 9395.6 ms | 后端喂入不足 |
| 64 | 1424.95 | 5945.7 ms | 5993.3 ms | 8690.7 ms | 混合流量保守候选 |
| 96 | 1537.09 | 5472.7 ms | 5767.3 ms | 7689.7 ms | 纯 90 秒最佳候选 |
| 128 | 1512.05 | 5622.4 ms | 5791.7 ms | 9114.8 ms | 已过吞吐拐点 |

短音频实测：10 秒、并发 96 时约 1419.20 audio_s/s、P95 693.0 ms；并发 128 时约
1463.32 audio_s/s、P95 894.8 ms。增加并发只有约 3.1% 吞吐收益，但 P95 增加约 29%。

## 3. 标准测试方法

1. 固定代码 tag、模型 revision、GPU、驱动/CUDA、依赖版本和音频文件 SHA256。
2. 服务启动后先预热至少 3 条；每组测试至少三轮，报告中位数而不是最好一轮。
3. 每轮只改一个变量；同时记录成功率、audio_s/s、原始 QPS、后端分片 RPS、P50/P95/P99、
   GPU 利用率/显存、CPU 和返回文本长度。
4. 性能调优后重新执行全量 CER，防止切片或版本变化造成精度退化。
5. 混合流量必须按真实时长分布回放；单一 90 秒结果不能代表 80% 为 0～20 秒的在线业务。

短音频基线：

```bash
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 96 --total 2000
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 128 --total 2000
```

现有仓库没有 90 秒测试音频。测试纯长音频时，应使用业务方实际准备并确认时长的文件，不要
引用不存在的文件；例如：

```bash
CHUNK_CONCURRENCY=3 LONG_CHUNKS_IN_FLIGHT=96 bash run.sh
python tests/test_service.py --api-mode chinese-asr \
  --audio /data/asr/verified_90s.wav --concurrency 96 --total 2000 --chunk-seconds 32
```

依次重启服务测试 `LONG_CHUNKS_IN_FLIGHT=32/64/96/128`。`--chunk-seconds` 仅用于压测器
计算预期分片数，必须与 `AUDIO_CHUNK_SECONDS` 相同，不会改变服务端切片。

## 4. 指标解释

- 原始请求 QPS：完整客户端请求的成功数/秒。
- 后端分片 RPS：成功请求对应分片总数/秒；长音频会高于原始 QPS。
- audio_s/s：成功请求数 × 原音频秒数 / 总耗时，是跨时长比较的主要吞吐指标。
- P95/P99：在线容量决策必须使用的尾延迟；吞吐小幅上升但尾延迟显著恶化通常已过拐点。
- `X-Audio-Chunks`：应与真实采样帧计算的预期分片一致；32.063 秒会切为 2 片。

## 5. 0～2000 秒混合流量

业务中 0～20 秒占 80% 时，优先保护短请求：

- 当前从 `CHUNK_CONCURRENCY=3`、`LONG_CHUNKS_IN_FLIGHT=96` 开始复测；
- 为各时长桶分别报告 P95/P99，不只报告全局平均；
- 与 64、128 做同条件对照，验证 96 在默认同卡 Aligner 模式下仍处于可接受拐点；
- 现有 A10 纯长音频数据中 128 的吞吐低于 96 且 P99 恶化，该历史结论必须保留；
- 当前短请求不占长分片信号量，生产入口仍应在上层 Gateway/LB 设置总请求限流和有界排队。

## 6. 同卡 ForcedAligner 试验

默认时间戳模式使用 `ALIGNER_DEVICE=cuda:0`、`bfloat16`、并发 1、batch 1；vLLM 默认显存
预算为 0.85。测试时同时记录 vLLM 与 Aligner 的总显存峰值、OOM、ASR 吞吐、
对齐耗时和端到端 P95/P99。分别测试关闭时间戳、仅字/词级、仅句级、两者同时开启；低流量
可运行不代表并发 96/总请求 2000 可安全上线。

## 7. 结果记录模板

每次发布记录：代码 tag、模型 revision、GPU/驱动、参数、音频时长/字符数、总请求、并发、
成功/失败、总耗时、QPS、分片 RPS、audio_s/s、P50/P95/P99、GPU/CPU、CER 和测试日期。
未经相同条件复测的数据不得直接横向比较。

## 8. v2.0 → v3.0 性能工程目标

本节是 `dev` 分支的长期优化路线。目标是在不破坏 API、CER、真实语种和真实时间戳契约的
前提下，提高单 GPU 有效吞吐、降低目标时长桶 P95/P99，并建立可复现、可回滚、可累计的
实验体系。候选技术不等于已实现能力；只有完成同条件对照并通过门禁后才能标记为“采纳”。

不可突破的边界：

- 继续使用原生 `vllm[audio]==0.16.0` 数据面，每张 GPU 一个 vLLM，不恢复自建
  Transformers/FastAPI GPU 层或应用固定 batcher；
- 模型仅使用 ModelScope 固定 revision，不引入 Hugging Face 下载链路；
- 不通过关闭错误检查、伪造语种/时间戳、静默跳过 Aligner 或放宽 CER 来换吞吐；
- VAD、重叠切片和跨片去重属于独立准确率功能，当前未实现，不能作为现成性能能力；
- 依赖保持精确固定并使用独立环境，不与 Paraformer、funasr、TensorRT 或 Transformers 5.x
  混装。

## 9. 当前推理阶段与可观测瓶颈

```text
HTTP 接收
  ├─ /chinese_asr：JSON 解析 → Base64 解码
  └─ multipart：字段读取
        ↓
libsndfile 校验 → >32 秒同步解码/PCM16 WAV 切片
        ↓
单请求 CHUNK_CONCURRENCY=3 + 全局 LONG_CHUNKS_IN_FLIGHT=96
        ↓
aiohttp 连接池 → vLLM scheduler → Qwen3-ASR
  ├─ 自动语种：Chat API + 分片二次 Base64 data URL
  └─ 显式语种：Transcriptions API + to_language
        ↓
ForcedAligner（默认同卡、并发 1、batch 1）→ 句级聚合
        ↓
结果序列化 → 有界异步日志 → HTTP 响应
```

当前已知而尚未量化完整的瓶颈：

1. `_split_audio` 在 aiohttp 事件循环中同步执行 libsndfile 解码和 WAV 重编码；并发长音频可能
   阻塞短请求、健康检查和后端响应处理。
2. 首轮网关 `ClientSession` 使用 aiohttp 默认连接池（总上限 100、空闲保留 15 秒）；目标机
   复现 `ServerDisconnectedError`，表明部分连接在池中等待期间先被 vLLM 关闭。现已采纳保持
   上限 100、仅把客户端空闲保留时间缩短为 4 秒的修复，六轮累计 12000/12000。
3. 短音频绕过长分片信号量，网关没有总请求准入和短长公平调度；它既可能保护短请求，也可能
   在突发流量下无界挤压后端，必须用混合流量验证。
4. 自动语种走 Chat API，每片生成 Base64 data URL 和 JSON；相对 multipart/显式语种存在额外
   CPU、内存复制和传输成本，但不能在丢失真实 `slid` 的情况下直接替换。
5. ForcedAligner 默认与 vLLM 同卡，是第二个 CUDA 进程，并且跨请求默认串行；ASR 吞吐提高后
   可能把瓶颈转移到对齐队列。
6. 长音频先被网关解码/重编码，Aligner 又解码分片；减少重复解码可能提速，但缓存全部 PCM
   会增加 2000 秒请求的 RSS。
7. 当前日志已异步化，但完整 `result_json` 的格式化和写入仍消耗 CPU/磁盘；只有实测证明是
   瓶颈后才考虑采样，错误摘要和请求关联不得丢失。
8. 现有压测只有端到端延迟、吞吐和粗粒度 GPU/CPU 采样，缺少接收、切片、信号量等待、连接
   等待、vLLM 排队/执行、Aligner 排队/执行、序列化等阶段数据，不能靠猜测决定参数。

## 10. 指标与默认晋级门禁

每个实验必须先声明主要优化目标和保护指标。没有同硬件、同数据、同代码基线的结果不得晋级。
初始工程门禁如下；业务 SLO 明确后可收紧，但必须在实验记录中说明：

- 正确性：成功率 100%，业务错误契约、分片顺序、语种和时间戳单调性不变；
- 准确率：使用同一参考集通过既定 CER 门禁；涉及切片、精度或模型输入的实验必须报告逐样本
  CER 差异，不允许只看总平均；
- 稳定性：无 OOM、NaN、死锁、请求泄漏或静默降级，连续三轮结果可重复；
- 性能：主要指标至少满足“`audio_s/s` 提升 5%”或“目标时长桶 P95/P99 降低 10%”之一；
- 保护：0～20 秒短请求 P99、失败率和 CER 不得为了长音频吞吐明显退化，默认性能退化上限 5%；
- 资源：报告 GPU 显存峰值、GPU 利用率、CPU、网关 RSS；显存必须保留可解释的安全余量；
- 证据：至少预热 3 条、正式执行 3 轮，以中位数决策，并保留最差一轮说明。

绝对吞吐或延迟目标必须在 `PERF-BASE-001` 基线完成后填写，不能从历史异条件数据推导。

### 11.1 网关与 CPU 路径

优先执行阶段计时，再决定是否实现有界线程池。线程池必须同时限制工作线程数、排队任务数和
在途原始音频字节；仅调用无界 `asyncio.to_thread` 会把事件循环阻塞转化为内存排队。验证需
同时观察 event-loop lag、`/health` 延迟、CPU、RSS、短请求 P99、切片 SHA256/时长和 CER。

连接池优化必须让 `limit`、`limit_per_host`、keep-alive 和连接等待时间可观测，并与网关总准入
共同设计。不能只把连接上限从 100 改大；若 vLLM 已饱和，更大连接池只会把等待转移到后端。
首轮基线及诊断轮已通过异常 cause 链确认毫秒级失败均为 `ServerDisconnectedError`。aiohttp
默认把空闲连接保留 15 秒；默认时间戳路径受串行 Aligner 限制，客户端约 8～9 秒后才补发请求，
连接可能先被 vLLM 关闭。采纳方案保持总连接和单主机连接上限 100，只将客户端空闲保留时间
设为 4 秒，使网关先清理陈旧连接；不自动重试可能已经提交的 POST。目标机六轮累计
12000/12000，中位吞吐仅下降 1.09%，P95/P99 分别上升 2.54%/4.07%，已通过保护门禁。

### 11.2 vLLM 与切片

`VLLM_MAX_NUM_SEQS`、`VLLM_MAX_NUM_BATCHED_TOKENS`、显存比例、切片长度和客户端并发相互
影响，但第一轮必须单变量；确认局部方向后才允许正交或网格实验。每组记录 waiting/running
requests、KV cache、GPU 利用率和显存。0.6B 模型通常不需要在单请求上做张量并行，多 GPU
优先采用每卡一个实例的水平扩展。

更大切片可减少 HTTP、Base64、重编码、调度和 Aligner 调用次数，但会增加单序列上下文、显存
和尾延迟；更小切片增加调度灵活性，却可能放大边界 CER 与请求开销。最终值由速度和 CER 共同
决定，不能仅依据纯 90 秒吞吐。

### 11.3 ForcedAligner

先分别测量 ASR-only 与默认时间戳，量化 Aligner 税负，再比较同卡与独立 GPU。`batch_size`
当前只在单条长请求内部合并分片，不是跨请求动态批处理；跨请求微批是新的高风险调度功能，
必须有最大等待时间、最大 batch、取消处理和回退路径。提高 `ALIGNER_CONCURRENCY` 前必须确认
模型对象并发调用安全，不能仅因配置允许就直接上线。

### 11.4 协议、复制与日志

`/chinese_asr` 自动语种为保留真实 `slid` 使用 Chat API，不能无证据切换到不返回语言标签的
路径。可控客户端优先用 multipart 或显式语言只能作为部署建议，不能删除兼容接口。PCM 复用、
流式 Base64 解码和临时文件方案必须分别核算 CPU、复制字节、RSS、磁盘 I/O 和清理失败风险。

日志采样只有在 `PERF-OBS-002` 证明序列化/磁盘是主要瓶颈且业务批准后实施。错误、启动、OOM、
丢弃计数、请求 ID 和统计摘要必须全量保留，不能用关闭日志掩盖性能问题。

### 11.5 暂不优先的技术

- 推测解码：ASR 输出相对短，且需要额外草稿模型和兼容验证，当前收益/复杂度比低；
- 自建 PyTorch/TensorRT 推理后端：违反单一 vLLM 数据面与独立环境约束，不纳入本轮；
- VAD/重叠切片：可能减少静音计算或改善边界，但会改变语义和 CER，必须作为独立功能评审；
- 无界队列、无限并发或固定 sleep 攒批：可能提高局部吞吐，却会破坏尾延迟和稳定性，禁止上线；
- 未验证量化模型：不得覆盖当前 ModelScope 固定 revision 目录，也不得以局部样本代替 CER 门禁。

## 12. 标准基线矩阵

`PERF-BASE-001` 至少覆盖：

| 维度 | 必测值 |
|---|---|
| API | `/chinese_asr`、`/v1/audio/transcriptions` |
| 语种路径 | 自动语种、显式 Chinese、显式 English、至少一种 Aligner 不支持语种 |
| 时间戳 | 全关、仅 words、仅 sentence、全部开启 |
| 时长 | 10、30、90、300、2000 秒或最接近的已确认样本 |
| 并发 | 1、32、64、96、128；超过安全范围时记录停止原因 |
| 流量 | 单一时长、80% 0～20 秒 + 20% 长音频的业务近似混合流量 |
| 质量 | CER、分片数、语言标签、words/句级时间戳单调和边界 |
| 资源 | GPU 利用率/显存、CPU、网关 RSS、vLLM waiting/running、日志丢弃 |

仓库当前没有可复现的 90/300/2000 秒标准集；测试负责人必须生成不含敏感数据的 manifest，
记录路径或数据集 ID、SHA256、采样率、声道、时长、语言和参考文本版本。原始业务音频不得因
建立基线而自动提交 Git。

## 13. 实验生命周期与 Git/Tag 规则

1. 在 [性能实验台账](性能实验台账.md) 创建唯一 ID，写清假设、唯一变量、基线、门禁和回滚值。
2. `dev` 上实现最小改动；先静态验证，再在目标 Linux/CUDA 环境运行相同矩阵三轮。
3. 保存机器可读摘要、环境和命令；原始日志、模型、音频和敏感业务正文不进入 Git。
4. 将结果追加到台账：`采纳`、`拒绝` 或 `阻塞`，拒绝记录不得删除。
5. 采纳后同步配置、README、使用说明、技术文档、发布验收和修改日志；默认值变化必须同步
   `src/config.py`、`run.sh`、`run_gateway.sh` 与 Compose。
6. 只有形成可复现的重要性能里程碑才创建带注释 tag；普通实验和失败实验只提交不打 tag。
   建议里程碑使用 `v2.1.0`、`v2.2.0` 等，最终验收发布使用 `v3.0.0`。tag 必须指向已经推送、
   通过门禁且文档完整的 `dev` 提交，不移动、不覆盖。
7. v3.0.0 发布前由验收后的 `dev` 合并到 `main`；实验期间不直接在 `main` 修改。

每个实验建议保留以下产物：

```text
performance-results/<实验ID>/
├── environment.json      代码、tag、依赖、GPU、驱动/CUDA、模型 manifest 摘要
├── dataset.json          音频 ID/SHA256/时长/语言/参考版本，不含敏感正文
├── command.txt           完整启动和压测命令
├── run-01.json           第一轮机器可读结果
├── run-02.json           第二轮机器可读结果
├── run-03.json           第三轮机器可读结果
└── decision.md           中位数、门禁、结论和回滚值
```

压测器现可通过 `--output-json` 原子生成单份 `schema_version=1` 报告，包含环境、输入摘要、
结果、阶段分位数、资源和前后指标快照；最多保留 20 个失败样本的状态、错误、请求 ID、延迟和
分片数，以便关联网关与 vLLM 日志，不保存音频内容。仍可按实验需要拆分为上述目录结构。原始
日志和敏感数据是否入库由数据敏感性和体积决定，至少将去敏摘要与结论写入台账。

## 14. 首轮实施顺序

1. `PERF-OBS-001/002`：实现已完成并通过假后端；在目标 GPU 校准采集开销和计时覆盖率；
2. `PERF-BASE-001`：冻结数据 manifest，建立 ASR-only 与默认 Aligner 三轮机器可读基线；
3. `PERF-LOAD-001`：补混合时长回放，建立短请求 P99 保护线；
4. `PERF-ALI-001/002`：量化并优化当前最可疑的同卡串行 Aligner；
5. `PERF-GW-001` 与 `PERF-NET-001`：依据阶段数据解决事件循环和连接等待；
6. `PERF-CHUNK-001` 与 `PERF-VLLM-001`：在固定拓扑下联合寻找调度拐点；
7. P2/P3 策略只有在 P0/P1 证据显示值得投入时进入实现。

每完成一轮都更新策略状态、台账和下一轮假设。任何收益若不能在相同条件下复现，立即回滚到
实验记录中的基线值，不带入后续实验。
