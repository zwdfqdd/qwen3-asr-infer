# 性能调优与基准（v1.0.0）

## 1. 参数分层

不要混淆以下四种并发：

| 参数 | v1.0.0 默认值 | 含义 |
|---|---:|---|
| `VLLM_MAX_NUM_SEQS` | 128 | vLLM scheduler 最大活跃序列数，不是固定 batch |
| `CHUNK_CONCURRENCY` | 3 | 单个长音频最多同时提交的分片数 |
| `LONG_CHUNKS_IN_FLIGHT` | 64 | 全局长音频分片在途上限，短音频不占用 |
| 压测 `--concurrency` | 96 | 客户端同时发送的原始请求数 |

v1.0.0 采用 `3/64` 作为 0～300 秒混合在线流量的保守默认值。纯 90 秒吞吐优先时，A10
实测候选为 `3/96`；不能把该值直接复制到其他 GPU 或流量分布。

## 2. 已有 A10 实测

测试条件：单张 A10、90 秒音频、2000 请求、客户端并发 96、每条切为 3 片、
`CHUNK_CONCURRENCY=3`。数据来自实际测试记录，未在本次 Windows 文档整理中重跑。

| LONG_CHUNKS_IN_FLIGHT | audio_s/s | 平均延迟 | P95 | P99 | 结论 |
|---:|---:|---:|---:|---:|---|
| 32 | 1136.31 | 7434.6 ms | 7512.1 ms | 9395.6 ms | 后端喂入不足 |
| 64 | 1424.95 | 5945.7 ms | 5993.3 ms | 8690.7 ms | 混合流量保守候选 |
| 96 | 1537.09 | 5472.7 ms | 5767.3 ms | 7689.7 ms | 纯 90 秒最佳候选 |
| 128 | 1512.05 | 5622.4 ms | 5791.7 ms | 9114.8 ms | 已过吞吐拐点 |

短音频实测：10 秒、并发 96 时约 1419.20 audio_s/s、P95 693.0 ms；并发 128 时约
1463.32 audio_s/s、P95 894.8 ms。增加并发只有约 3.1% 吞吐收益，但 P95 增加约 29%。

## 3. 标准测试方法

1. 固定代码 tag、模型 revision、GPU、驱动/CUDA、依赖版本和音频文件 SHA256。
2. 服务启动后先预热至少 3 条；每组测试至少三轮，报告中位数而不是最好一轮。
3. 每轮只改一个变量；同时记录成功率、audio_s/s、原始 QPS、后端分片 RPS、P50/P95/P99、
   GPU 利用率/显存、CPU 和返回文本长度。
4. 性能调优后重新执行全量 CER，防止切片或版本变化造成精度退化。
5. 混合流量必须按真实时长分布回放；单一 90 秒结果不能代表 80% 为 0～20 秒的在线业务。

短音频基线：

```bash
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 96 --total 2000
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 128 --total 2000
```

现有仓库没有 90 秒测试音频。测试纯长音频时，应使用业务方实际准备并确认时长的文件，不要
引用不存在的文件；例如：

```bash
CHUNK_CONCURRENCY=3 LONG_CHUNKS_IN_FLIGHT=64 bash run.sh
python tests/test_service.py --api-mode chinese-asr \
  --audio /data/asr/verified_90s.wav --concurrency 96 --total 2000
```

依次重启服务测试 `LONG_CHUNKS_IN_FLIGHT=32/64/96/128`。`--chunk-seconds` 仅用于压测器
计算预期分片数，必须与 `AUDIO_CHUNK_SECONDS` 相同，不会改变服务端切片。

## 4. 指标解释

- 原始请求 QPS：完整客户端请求的成功数/秒。
- 后端分片 RPS：成功请求对应分片总数/秒；长音频会高于原始 QPS。
- audio_s/s：成功请求数 × 原音频秒数 / 总耗时，是跨时长比较的主要吞吐指标。
- P95/P99：在线容量决策必须使用的尾延迟；吞吐小幅上升但尾延迟显著恶化通常已过拐点。
- `X-Audio-Chunks`：应与真实采样帧计算的预期分片一致；30.063 秒会切为 2 片。

## 5. 0～300 秒混合流量

业务中 0～20 秒占 80% 时，优先保护短请求：

- 从 `CHUNK_CONCURRENCY=3`、`LONG_CHUNKS_IN_FLIGHT=64` 开始；
- 为各时长桶分别报告 P95/P99，不只报告全局平均；
- 若 GPU 未持续饱和且长音频积压，再试 96；若短请求尾延迟明显上涨则退回 64；
- 128 在现有 A10 纯长音频测试中吞吐已下降且 P99 恶化，不作为默认值；
- 当前短请求不占长分片信号量，生产入口仍应在上层 Gateway/LB 设置总请求限流和有界排队。

## 6. 结果记录模板

每次发布记录：代码 tag、模型 revision、GPU/驱动、参数、音频时长/字符数、总请求、并发、
成功/失败、总耗时、QPS、分片 RPS、audio_s/s、P50/P95/P99、GPU/CPU、CER 和测试日期。
未经相同条件复测的数据不得直接横向比较。
