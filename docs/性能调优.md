# 性能调优与基准（v2.1.0）

## 1. 参数分层

不要混淆以下四种并发：

| 参数 | 当前默认值 | 含义 |
|---|---:|---|
| `VLLM_MAX_NUM_SEQS` | 128 | vLLM scheduler 最大活跃序列数，不是固定 batch |
| `CHUNK_CONCURRENCY` | 3 | 单个长音频最多同时提交的分片数 |
| `LONG_CHUNKS_IN_FLIGHT` | 96 | 全局长音频分片在途上限，短音频不占用 |
| 压测 `--concurrency` | 96 | 客户端同时发送的原始请求数 |

v1.0.0 发布时采用 `3/64`；v2.0.0 统一为 `3/96` 和 32 秒分片，输入上限当前为 0～7500 秒。
下表历史 A10 数据显示纯 90 秒的 `3/96` 吞吐最高；默认同卡 ForcedAligner 和真实混合流量
仍须在发布前复测。

## 2. 已有 A10 实测

测试条件：单张 A10、90 秒音频、2000 请求、客户端并发 96、每条切为 3 片、
`CHUNK_CONCURRENCY=3`。数据来自实际测试记录，未在本次 Windows 文档整理中重跑。

| LONG_CHUNKS_IN_FLIGHT | audio_s/s | 平均延迟 | P95 | P99 | 结论 |
|---:|---:|---:|---:|---:|---|
| 32 | 1136.31 | 7434.6 ms | 7512.1 ms | 9395.6 ms | 后端喂入不足 |
| 64 | 1424.95 | 5945.7 ms | 5993.3 ms | 8690.7 ms | 混合流量保守候选 |
| 96 | 1537.09 | 5472.7 ms | 5767.3 ms | 7689.7 ms | 纯 90 秒最佳候选 |
| 128 | 1512.05 | 5622.4 ms | 5791.7 ms | 9114.8 ms | 已过吞吐拐点 |

短音频实测：10 秒、并发 96 时约 1419.20 audio_s/s、P95 693.0 ms；并发 128 时约
1463.32 audio_s/s、P95 894.8 ms。增加并发只有约 3.1% 吞吐收益，但 P95 增加约 29%。

## 3. 标准测试方法

1. 固定代码 tag、模型 revision、GPU、驱动/CUDA、依赖版本和音频文件 SHA256。
2. 服务启动后先预热至少 3 条；每组测试至少三轮，报告中位数而不是最好一轮。
3. 每轮只改一个变量；同时记录成功率、audio_s/s、原始 QPS、后端分片 RPS、P50/P95/P99、
   GPU 利用率/显存、CPU 和返回文本长度。
4. 性能调优后重新执行全量 CER，防止切片或版本变化造成精度退化。
5. 混合流量必须按真实时长分布回放；单一 90 秒结果不能代表 80% 为 0～20 秒的在线业务。

短音频基线：

```bash
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 96 --total 2000
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 128 --total 2000
```

现有仓库没有 90 秒测试音频。测试纯长音频时，应使用业务方实际准备并确认时长的文件，不要
引用不存在的文件；例如：

```bash
CHUNK_CONCURRENCY=3 LONG_CHUNKS_IN_FLIGHT=96 bash run.sh
python tests/test_service.py --api-mode chinese-asr \
  --audio /data/asr/verified_90s.wav --concurrency 96 --total 2000 --chunk-seconds 32
```

依次重启服务测试 `LONG_CHUNKS_IN_FLIGHT=32/64/96/128`。`--chunk-seconds` 仅用于压测器
计算预期分片数，必须与 `AUDIO_CHUNK_SECONDS` 相同，不会改变服务端切片。

## 4. 指标解释

- 原始请求 QPS：完整客户端请求的成功数/秒。
- 后端分片 RPS：成功请求对应分片总数/秒；长音频会高于原始 QPS。
- audio_s/s：成功请求数 × 原音频秒数 / 总耗时，是跨时长比较的主要吞吐指标。
- P95/P99：在线容量决策必须使用的尾延迟；吞吐小幅上升但尾延迟显著恶化通常已过拐点。
- `X-Audio-Chunks`：应与真实采样帧计算的预期分片一致；32.063 秒会切为 2 片。

## 5. 0～7500 秒混合流量

业务中 0～20 秒占 80% 时，优先保护短请求：

- 当前从 `CHUNK_CONCURRENCY=3`、`LONG_CHUNKS_IN_FLIGHT=96` 开始复测；
- 为各时长桶分别报告 P95/P99，不只报告全局平均；
- 与 64、128 做同条件对照，验证 96 在默认同卡 Aligner 模式下仍处于可接受拐点；
- 现有 A10 纯长音频数据中 128 的吞吐低于 96 且 P99 恶化，该历史结论必须保留；
- 当前短请求不占长分片信号量，生产入口仍应在上层 Gateway/LB 设置总请求限流和有界排队；
- 当前默认保持 `ALIGNER_CONCURRENCY=1`、`ALIGNER_BATCH_SIZE=1`；已实现有界跨请求动态微批。
  batch=32 当前达到 220.03 audio_s/s，是最佳平衡候选；batch=48 仅再增 4.1%，同时 P95 恶化
  4.9%、显存升至 21821 MiB，拒绝继续放大 batch。固定 batch=32 后，worker=2 吞吐仅 +3.7%、
  执行墙钟 +91.3%，也被拒绝。attention=auto 已确认实际为 SDPA，当前固定镜像缺少
  `flash_attn`，显式 FA2 阻塞。worker=1/batch=32/attention=auto 的批内阶段诊断显示 WAV 解码、
  官方 `model.align()`、结果构建占比约 20.3%/79.2%/0.5%；新增默认回滚值为 1 的
  `ALIGNER_DECODE_WORKERS` 后，workers=4 解码仅 -9.52%、模型调用 +0.81%、吞吐 +1.34%、P95
  -2.31%，未达到门禁，已拒绝并恢复 1，不再扩大线程数。下一解码方向只能作为新的有界预解码
  重叠实验；重复性、混合流量、时间戳与 CER 门禁完成前，不能提前写成生产收益。
- 历史默认时间戳结果的 `aligner-queue` 约占总耗时 94%，是 `PERF-ALI-003` 的对照基线。

## 6. 同卡 ForcedAligner 试验

默认时间戳模式使用 `ALIGNER_DEVICE=cuda:0`、`bfloat16`、单 worker；生产默认 batch=32，
设为 1 为逐片回滚值。
目标 A10 已按单变量完成 batch=4/8/16/32/48 性能探索；batch=32 是当前最佳平衡候选，batch=48
因吞吐收益不足 5%、P95 接近退化上限且显存峰值达到 21821 MiB 被拒绝。batch=32 下 worker=2
同样因吞吐收益不足 5% 和执行墙钟翻倍被拒绝。attention=auto 已确认实际为 SDPA，FA2 因固定
镜像缺少依赖而阻塞。batch=32 批内阶段显示 WAV 解码占三项合计约 20.3%；固定其他参数测试
`ALIGNER_DECODE_WORKERS=4` 后，解码仅 -9.52%、模型调用 +0.81%、吞吐 +1.34%、P95 -2.31%，
未达到晋级线，已拒绝并恢复 1，不再测试其他线程数。若继续处理解码成本，应新建有界预解码
流水线实验，让 CPU 工作与 ASR 阶段重叠。测试时仍需记录 vLLM 与 Aligner 的总显存峰值、OOM、
ASR 吞吐、三项批内耗时和端到端 P95/P99。分别测试关闭时间戳、仅字/词级、仅句级、两者同时
开启；低流量可运行不代表并发 96/总请求 2000 可安全上线。

## 7. 结果记录模板

每次发布记录：代码 tag、模型 revision、GPU/驱动、参数、音频时长/字符数、总请求、并发、
成功/失败、总耗时、QPS、分片 RPS、audio_s/s、P50/P95/P99、GPU/CPU、CER 和测试日期。
未经相同条件复测的数据不得直接横向比较。

## 8. v2.0 → v3.0 性能工程目标

本节是 `dev` 分支的长期优化路线。目标是在不破坏 API、CER、真实语种和真实时间戳契约的
前提下，提高默认时间戳链路吞吐并降低目标时长桶 P95/P99。现有证据显示 ASR-only 中位吞吐
为 1141.75 audio_s/s，而同卡 PyTorch ForcedAligner 在 batch=32 附近只有约 220 audio_s/s；
因此主矛盾已经从网关参数和 ASR scheduler 转为 **ForcedAligner 执行后端与服务拓扑**。
batch、worker、attention、解码线程和预解码路线已经完成定位并收敛，不再把局部参数搜索列为
下一阶段主线。

不可突破的边界：

- 当前主链统一固定 `vllm[audio]==0.19.1`（CUDA 12.9），并保留 `transformers==4.57.6` 与
  `qwen-asr==0.0.6` PyTorch ForcedAligner；版本上限由宿主驱动 535 决定，不允许安装第二个
  vLLM、不得引入 CUDA 13 构建，也不得在 Aligner 迁移前单独升级 Transformers 5.x；
- `PERF-ARCH-001` 后续只验证 token-classify Aligner；在独立 spike 通过 11 种语言、时间戳和
  吞吐门禁前，不修改当前 `src/aligner.py`，也不宣称已经完成架构迁移；
- 模型只使用 ModelScope 固定 revision 的本地权重，不引入 Hugging Face 下载链路；
- 不通过关闭错误检查、伪造语种/时间戳、静默跳过 Aligner 或放宽 CER 来换吞吐；
- VAD、重叠切片和跨片去重属于独立准确率功能，当前未实现，不能作为现成性能能力；
- 候选技术不等于已实现能力；只有完成同硬件、同数据、同请求矩阵对照并通过架构级门禁后，
  才能标记为“采纳”并进入生产集成评审。

## 9. 当前推理阶段与可观测瓶颈

```text
HTTP 接收
  ├─ /chinese_asr：JSON 解析 → Base64 解码
  └─ multipart：字段读取
        ↓
libsndfile 校验 → >32 秒同步解码/PCM16 WAV 切片
        ↓
单请求 CHUNK_CONCURRENCY=3 + 全局 LONG_CHUNKS_IN_FLIGHT=96
        ↓
aiohttp 连接池 → vLLM scheduler → Qwen3-ASR
  ├─ 自动语种：Chat API + 分片二次 Base64 data URL
  └─ 显式语种：Transcriptions API + to_language
        ↓
ForcedAligner（有界分片队列 → 跨请求动态 batch → 默认单 worker）→ 句级聚合
        ↓
结果序列化 → 有界异步日志 → HTTP 响应
```

当前已知而尚未量化完整的瓶颈：

1. `_split_audio` 在 aiohttp 事件循环中同步执行 libsndfile 解码和 WAV 重编码；并发长音频可能
   阻塞短请求、健康检查和后端响应处理。
2. 首轮网关 `ClientSession` 使用 aiohttp 默认连接池（总上限 100、空闲保留 15 秒）；目标机
   复现 `ServerDisconnectedError`，表明部分连接在池中等待期间先被 vLLM 关闭。现已采纳保持
   上限 100、仅把客户端空闲保留时间缩短为 4 秒的修复，六轮累计 12000/12000。
3. 短音频绕过长分片信号量，网关没有总请求准入和短长公平调度；它既可能保护短请求，也可能
   在突发流量下无界挤压后端，必须用混合流量验证。
4. 自动语种走 Chat API，每片生成 Base64 data URL 和 JSON；相对 multipart/显式语种存在额外
   CPU、内存复制和传输成本，但不能在丢失真实 `slid` 的情况下直接替换。
5. ForcedAligner 默认与 vLLM 同卡，是第二个 CUDA 进程，并且跨请求默认串行；ASR 吞吐提高后
   可能把瓶颈转移到对齐队列。
6. 长音频先被网关解码/重编码，Aligner 又解码分片；减少重复解码可能提速，但缓存全部 PCM
   会增加 2000 秒请求的 RSS。
7. 当前日志已异步化，但完整 `result_json` 的格式化和写入仍消耗 CPU/磁盘；只有实测证明是
   瓶颈后才考虑采样，错误摘要和请求关联不得丢失。
8. 当前已提供请求解析、Base64、切片、分片信号量等待、后端 HTTP、ASR 墙钟、Aligner
   排队/执行、后处理、序列化和总耗时；目标 GPU 基线覆盖率 100%。vLLM 内部预处理与 scheduler
   仍需结合 stderr 和 Prometheus 判断，不能把网关 `asr-backend` 直接解释为纯 GPU 推理时间。
9. ASR-only 曾因共享 Fast Tokenizer 的并发 Rust 借用冲突返回 HTTP 400；`PERF-TOK-001` 已用
   完整调用锁修复并通过 8000/8000。升级固定依赖或移除锁时必须把该错误作为回归门禁。

## 10. 指标与默认晋级门禁

每个实验必须先声明主要优化目标和保护指标。没有同硬件、同数据、同代码基线的结果不得晋级。
初始工程门禁如下；业务 SLO 明确后可收紧，但必须在实验记录中说明：

- 正确性：成功率 100%，业务错误契约、分片顺序、语种和时间戳单调性不变；
- 准确率：使用同一参考集通过既定 CER 门禁；涉及切片、精度或模型输入的实验必须报告逐样本
  CER 差异，不允许只看总平均；
- 稳定性：无 OOM、NaN、死锁、请求泄漏或静默降级，连续三轮结果可重复；
- 性能：主要指标至少满足“`audio_s/s` 提升 5%”或“目标时长桶 P95/P99 降低 10%”之一；
- 保护：0～20 秒短请求 P99、失败率和 CER 不得为了长音频吞吐明显退化，默认性能退化上限 5%；
- 资源：报告 GPU 显存峰值、GPU 利用率、CPU、网关 RSS；显存必须保留可解释的安全余量；
- 证据：至少预热 3 条、正式执行 3 轮，以中位数决策，并保留最差一轮说明。

绝对吞吐或延迟目标必须在 `PERF-BASE-001` 基线完成后填写，不能从历史异条件数据推导。

状态只允许：`候选`、`就绪`、`测试中`、`采纳`、`拒绝`、`阻塞`。拒绝项不删除，保留硬件、
版本和失败原因，以免重复试错。

| `PERF-ALI-005` | P1 | Aligner 单批内部阶段计时 | 采纳 | 区分解码、官方 model.align 与结果构建 | batch=32 占比约 20.3%/79.2%/0.5%，已定位下一优化点 |
| `PERF-ALI-006` | P1 | Aligner 批内有界并行 WAV 解码 | 拒绝 | 降低每批 CPU 解码墙钟 | workers=4 解码仅 -9.52%、吞吐仅 +1.34%；恢复 1，不测试其他线程数 |
| `PERF-ALI-008` | P0 | 单卡双 CUDA 进程重叠（MPS） | 阻塞 | 回收 GPU 空转，不换后端 | 双向三轮中位吞吐 +19.97%、P95 -16.32%；四项故障场景均无连坐；但 daemon 缺失时会静默降级 17.8% 且无告警，须先加启动校验 |
| `PERF-ALI-007` | P1 | 有界预解码与 ASR 阶段重叠 | 拒绝 | 从 Aligner 关键路径隐藏 WAV 解码 | 命中 100% 但模型调用 +23.15%、吞吐仅 +1.84%；恢复默认关闭 |
| `PERF-COPY-001` | P2 | ASR/Aligner 复用受控 PCM 或减少重复解码 | 候选 | 降低 CPU 与内存复制 | 2000 秒音频 RSS，生命周期和释放复杂 |
| `PERF-PROTO-001` | P2 | 量化 multipart、Base64、自动/显式语种成本 | 候选 | 减少编码和 JSON 复制 | 不能破坏 Base64 业务接口或真实 `slid` |
| `PERF-LOG-001` | P2 | 可配置成功业务 JSON 采样，错误全量保留 | 阻塞 | 降低 CPU/磁盘压力 | 先确认审计要求并证明日志确为瓶颈 |
| `PERF-DEPLOY-001` | P2 | 多 GPU 单卡单实例水平扩展与上层负载均衡 | 候选 | 近线性扩容和故障隔离 | 不在单实例内启动多个 vLLM 抢同卡 |
| `PERF-RND-001` | P3 | INT8/量化权重兼容性研究 | 阻塞 | 可能降低显存/提高吞吐 | A10/多模态模型/vLLM 支持未验证，需独立模型目录和 CER 全量门禁 |
| `PERF-RND-002` | P3 | processor/prefix 缓存、编译图和 CUDA Graph 深化 | 阻塞 | 可能减少重复前处理或内核开销 | vLLM 已管理 CUDA Graph；独特音频缓存命中率可能很低 |

### 11.1 网关与 CPU 路径

优先执行阶段计时，再决定是否实现有界线程池。线程池必须同时限制工作线程数、排队任务数和
在途原始音频字节；仅调用无界 `asyncio.to_thread` 会把事件循环阻塞转化为内存排队。验证需
同时观察 event-loop lag、`/health` 延迟、CPU、RSS、短请求 P99、切片 SHA256/时长和 CER。

连接池优化必须让 `limit`、`limit_per_host`、keep-alive 和连接等待时间可观测，并与网关总准入
共同设计。不能只把连接上限从 100 改大；若 vLLM 已饱和，更大连接池只会把等待转移到后端。
根因观测确认毫秒级失败为 `ServerDisconnectedError`。aiohttp 默认把空闲连接保留 15 秒；默认时间戳路径受串行 Aligner 限制，客户端约 8～9 秒后才补发请求，
连接可能先被 vLLM 关闭。采纳方案保持总连接和单主机连接上限 100，只将客户端空闲保留时间
设为 4 秒，使网关先清理陈旧连接；不自动重试可能已经提交的 POST。目标机六轮累计
12000/12000，中位吞吐仅下降 1.09%，P95/P99 分别上升 2.54%/4.07%，已通过保护门禁。

### 11.2 vLLM 与切片

`VLLM_MAX_NUM_SEQS`、`VLLM_MAX_NUM_BATCHED_TOKENS`、显存比例、切片长度和客户端并发相互
影响，但第一轮必须单变量；确认局部方向后才允许正交或网格实验。每组记录 waiting/running
requests、KV cache、GPU 利用率和显存。0.6B 模型通常不需要在单请求上做张量并行，多 GPU
优先采用每卡一个实例的水平扩展。

更大切片可减少 HTTP、Base64、重编码、调度和 Aligner 调用次数，但会增加单序列上下文、显存
和尾延迟；更小切片增加调度灵活性，却可能放大边界 CER 与请求开销。最终值由速度和 CER 共同
决定，不能仅依据纯 90 秒吞吐。

### 11.3 ForcedAligner

ASR-only 与默认时间戳的 10 秒历史基线已经建立；旧实现的主要差异来自串行 Aligner 排队。
当前已实现跨请求有界动态微批：`ALIGNER_BATCH_SIZE` 是单次官方 `align()` 的跨请求物理分片
上限，`ALIGNER_BATCH_WAIT_MS` 从首条任务起限定等待，队列达到 batch 上限立即发车；
`ALIGNER_QUEUE_SIZE` 提供背压，`ALIGNER_BATCH_SIZE=1` 可回滚为逐片模型调用。

目标 A10 已保持 `ALIGNER_CONCURRENCY=1`，按单变量完成 batch=4/8/16/32/48 性能探索；
batch=32 是当前最佳平衡候选，batch=48 因吞吐收益不足 5%、P95 接近保护线且显存达到
21821 MiB 被拒绝，不再继续 batch=64。固定 batch=32 后，worker=2 只获得 3.7% 吞吐提升，
同时 Aligner 执行墙钟增加 91.3%，因此拒绝共享模型并发并恢复 worker=1。

`PERF-ALI-004` 已确认 `auto` 实际为 `sdpa`；当前固定镜像缺少 `flash_attn`，显式 FA2
阻塞且不得运行时安装，因此 attention 路线结束。`PERF-ALI-005` 在
worker=1/batch=32/attention=auto 下测得每批 WAV 解码、官方 `model.align()` 和结果构建均值
281.12/1097.04/7.53 ms，占三项合计约 20.3%/79.2%/0.5%。解码已超过 10% 优化门槛，
结果构建可忽略，模型调用尚未达到 85%～90% 的软件层上限判断线。

`PERF-ALI-006` 使用 `ALIGNER_DECODE_WORKERS` 控制持久化固定大小线程池，只并行同批独立内存
WAV 解码，并按输入顺序交给官方模型；默认值 1 不创建线程池，保留串行回滚。固定
worker=1/batch=32/wait=5 ms/queue=256/attention=auto 的 workers=4 实验中，解码仅 -9.52%、
模型调用 +0.81%、吞吐 +1.34%、P95 -2.31%，因此拒绝并恢复 1，不测试其他线程数。

`PERF-ALI-007` 的有界预解码在目标 A10 命中 100%，残余等待 0.01 ms，成功把批内解码从
281.12 降至 0.03 ms；但与 vLLM ASR 同卡重叠使 `model.align()` 从 1097.04 增至
1351.02 ms（+23.15%），吞吐仅 +1.84%、P95 -1.58%，未达到门禁，因此拒绝并恢复默认关闭。
官方 `align()` 已使用 `torch.inference_mode()`；继续扩大 worker、队列、内存预算或插入人为
延迟都不能消除两个 GPU 进程的执行竞争。单卡软件路线至此收敛，下一步只进行 `PERF-ALI-001`
独立 Aligner GPU/实例拓扑对照；仍须覆盖三轮吞吐/尾延迟、CPU、RSS、显存、时间戳和 CER。

### 11.4 协议、复制与日志

`/chinese_asr` 自动语种为保留真实 `slid` 使用 Chat API，不能无证据切换到不返回语言标签的
路径。可控客户端优先用 multipart 或显式语言只能作为部署建议，不能删除兼容接口。PCM 复用、
流式 Base64 解码和临时文件方案必须分别核算 CPU、复制字节、RSS、磁盘 I/O 和清理失败风险。

日志采样只有在 `PERF-OBS-002` 证明序列化/磁盘是主要瓶颈且业务批准后实施。错误、启动、OOM、
丢弃计数、请求 ID 和统计摘要必须全量保留，不能用关闭日志掩盖性能问题。

### 11.5 时间戳获取方式的技术路线决策（2026-08-14 定稿，本阶段暂停）

结论：**继续使用 Qwen3-ForcedAligner，不自研帧对齐，不引入外部对齐栈。** 本节固化依据，
避免后续重复讨论。

不可行项及原因：

1. **主模型直接输出时间戳。** 官方实现要求 `return_time_stamps=True` 时必须提供
   `forced_aligner`，否则直接抛错；官方 demo 未提供 aligner 时会隐藏时间戳界面。Qwen3-ASR
   主模型不产出时间戳。
2. **按 CTC 方式从帧索引反推时间戳。** 官方音频编码器包含三个 `Conv2d(..., stride=2)`，
   时间轴共下采样 8 倍，按 10 ms 帧移即每帧 80 ms。该分辨率已被实测证实：真实响应的字级
   时间戳全部为 0.08 秒整数倍，`timestamp_segment_time` 即 80 ms。但主模型是
   `Qwen3ASRThinkerForConditionalGeneration` + `GenerationMixin.generate()` 的自回归解码，
   输出 token 数由文本长度决定，与音频帧数无对应关系，因此不存在可反推的帧到字符映射。
   要走帧同步必须新增 CTC 头并重新训练，需对齐监督数据，超出本项目范围。
3. **ForcedAligner 已是等价思路的工程实现。** 它复用同一音频塔与 Qwen3 骨干，将 LM 头替换为
   分类头，在 `<timestamp>` token 位置直接预测 80 ms 时间桶索引，把帧对齐问题转为桶分类
   问题。其时间分辨率与帧同步方案相同，因此自研帧对齐没有精度优势。
4. **外部 CTC 强制对齐（wav2vec2/MMS 等）。** `torchaudio.functional.forced_align` 已标记
   弃用，TorchAudio 自 2.9 起进入维护阶段，不适合作为新的生产依赖；同时需要额外声学模型
   权重与多语言罗马化处理，与本项目独立环境、精确固定依赖的约束冲突；官方称
   Qwen3-ForcedAligner 时间戳精度优于 E2E forced-alignment 模型，换用后需重做 11 种语言
   精度对比，收益上限不明确。
5. **从 attention 权重做 DTW。** Qwen3-ASR 为 decoder-only，音频嵌入拼入文本序列走
   self-attention；vLLM 不暴露 attention 权重，且需要挑选层与头并用标注数据调优，
   工程量大、精度不确定。
6. **用 VAD 或分片边界均摊伪造字级时间戳。** 明确禁止，属于伪造数据。

因此优化方向不是替换时间戳算法，而是**减少需要对齐的请求数与对齐单元数**，并提升对齐链路
的执行效率。保留路线见 11.6。外部资料内容均为转述。

### 11.6 执行后端架构路线

单卡 PyTorch 参数路线已经收敛，不再把 batch=64、更高 worker、更多解码线程、扩大预解码预算
或人为 sleep 列为候选。时间戳算法路线已按 11.5 定稿，本阶段暂停对齐后端替换。

按投入产出保留以下路线，顺序即建议执行顺序：

- **L1 生产默认值（已落地，待目标机回归）。** `ALIGNER_BATCH_SIZE` 默认已由 1 改为 32，
  端到端由 107.33 升到 228.57 audio_s/s；走 MPS 后达到 274.22，合计约 2.5 倍。零推理代码
  改动。`run.sh` 新增 `REQUIRE_MPS`（默认 false）强制校验：守护进程不可用或 vLLM 未接入时
  直接退出，避免实测到的 17.8% 静默降级。注意 MPS 是宿主级透明特性，服务侧无法关闭，因此
  该开关只表示“必须可用”；无论取值，启动都会声明实际接入状态，防止基线被静默启用污染。
  目标机已回归：默认 batch=32 且 MPS 在线时为 271.45 audio_s/s，与三轮中位 274.22 一致。
- **L2 按需对齐（未实现）。** 当前时间戳是进程级全局开关，一旦开启全部请求都走 Aligner。
  关闭时为 1102.95、开启时为 274.22 audio_s/s，相差约 4 倍。改为请求级参数后，若仅 20%
  请求需要时间戳，混合平均可达约 687 audio_s/s。收益完全取决于业务中时间戳请求占比，
  需先确认该比例；不得因此改变已开启请求的时间戳语义。
- **L3 分片级流水（未实现）。** 现网关为请求级串行：先等全部分片完成 ASR，再整体对齐。
  10 秒单片场景无影响，但 7500 秒上限对应约 235 个分片时两阶段完全不重叠。改为分片级流水
  可让 ASR 与对齐真正并行，属长音频结构性收益。
- **L4 降低对齐粒度（未实现）。** 官方支持任意单元的时间戳预测。当前按字对齐，每字两个
  `<timestamp>` token；若业务只需句级，可改用句子作为对齐单元，序列长度显著下降。这是
  能力取舍而非纯优化，必须业务确认后才可作为默认行为；PyTorch 后端需绕过官方内部分词，
  vLLM token-classify 天然支持自定义单元。
- **L5 `PERF-ARCH-001` token-classify 集成（原始性能已验证）。** batch=32 原始吞吐
  1180.51 audio_s/s，相对同口径 PyTorch 409.8 为 +188.1%。但 PyTorch 前向从 1097.04 ms
  优化到 780.82 ms（-28.8%）时端到端仅 +3.82%，说明端到端收益受进程拓扑而非前向算力决定；
  在拓扑问题解决前集成，很可能出现原始大幅提升而端到端几乎不变。
- **L6 `PERF-ALI-001` 独立 GPU 拓扑。** 需要第二张 GPU，属硬件与拓扑收益，不得计入单卡
  软件提升。
- **L7 `PERF-ARCH-002` TensorRT。** 条件触发，仅在 L5 未达架构门禁且剖析仍指向模型前向时启动。

下一阶段按以下顺序推进：

1. **主 ASR 0.19.1 发布验收。** 代码、依赖和镜像已完成版本迁移，但仍需关闭时间戳重跑
   API、语种、热词、长音频、Tokenizer、CER 和三轮 ASR-only 门禁；冻结的 0.16 结果只作为
   同硬件历史对照，未通过时回滚部署镜像。
2. **`PERF-ARCH-001`：vLLM token-classify Aligner spike。** 在当前单 Python 环境中验证
   Aligner 模型加载、输入构造、输出时间桶、多语言后处理和 batch 1/8/16/32 原始吞吐；通过
   Phase A/B 前不修改当前 PyTorch `src/aligner.py`。
3. **`PERF-ALI-001`：独立 GPU/实例拓扑。** 若目标机有两张 GPU，vLLM ASR 固定 `cuda:0`，
   候选 Aligner 服务固定 `cuda:1`；这属于额外硬件和拓扑收益，不得描述成单 GPU 软件提升。
4. **`PERF-ARCH-002`：TensorRT FP16/BF16 spike。** 仅当新版 vLLM Aligner 未达到架构级门禁
   时启动。CPU 保留官方 `encode_timestamp()`、音频/文本 processor、argmax 后的 timestamp
   mask、`parse_timestamp()`、单调性及边界校验；TensorRT 只覆盖 audio tower、
   thinker/backbone 和 token-classification head。首轮不做 INT8。
5. **INT8 与量化。** 只有 FP16/BF16 已完成 11 种语言、动态 shape、时间戳和 CER 对齐后，才
   能另立实验做校准与质量门禁；不得覆盖固定 revision 模型目录。

TensorRT 不是权重格式替换：需要可复现的 ONNX/导出图、batch 1/8/16/32、最长 32 秒音频及动态
文本长度 profile，还要维护模型特定后处理。候选后端应作为独立服务或 Triton/TensorRT 实例，
不能嵌入 aiohttp 事件循环，也不能把 TensorRT、ONNX 或新版 vLLM 安装到当前稳定容器。

架构级首轮门禁高于普通参数实验：Aligner 原始吞吐至少提升 30%，默认时间戳端到端吞吐至少提升
20%，成功率 100%；对齐单元文本和数量一致，时间戳严格单调、不越音频边界；11 种支持语言
全部通过，并完成三轮 2000 请求、混合时长、CER、取消/超时、服务故障和回滚验证。任一项不满足
则保持现有 PyTorch 实现，不以局部 P99 或单轮最好值晋级。

实现依据：[vLLM Token Classify 示例](https://docs.vllm.ai/en/latest/examples/pooling/token_classify/)
说明时间桶由 `<timestamp>` token 位置的分类结果得到；
[vLLM Qwen3 ForcedAligner 模型文档](https://docs.vllm.ai/en/v0.19.0/api/vllm/model_executor/models/qwen3_asr_forced_aligner/)
展示了音频塔、Qwen3 骨干和分类头的模型结构。外部资料内容均为转述，不代表当前稳定环境已经
支持该后端。

## 12. 标准基线矩阵

`PERF-BASE-001` 至少覆盖：

| 维度 | 必测值 |
|---|---|
| API | `/chinese_asr`、`/v1/audio/transcriptions` |
| 语种路径 | 自动语种、显式 Chinese、显式 English、至少一种 Aligner 不支持语种 |
| 时间戳 | 全关、仅 words、仅 sentence、全部开启 |
| 时长 | 10、30、90、300、2000 秒或最接近的已确认样本 |
| 并发 | 1、32、64、96、128；超过安全范围时记录停止原因 |
| 流量 | 单一时长、80% 0～20 秒 + 20% 长音频的业务近似混合流量 |
| 质量 | CER、分片数、语言标签、words/句级时间戳单调和边界 |
| 资源 | GPU 利用率/显存、CPU、网关 RSS、vLLM waiting/running、日志丢弃 |

仓库当前没有可复现的 90/300/2000 秒标准集；测试负责人必须生成不含敏感数据的 manifest，
记录路径或数据集 ID、SHA256、采样率、声道、时长、语言和参考文本版本。原始业务音频不得因
建立基线而自动提交 Git。

## 13. 实验生命周期与 Git/Tag 规则

1. 在 [性能实验台账](性能实验台账.md) 创建唯一 ID，写清假设、唯一变量、基线、门禁和回滚值。

   `src/config.py`、`run.sh`、`run_gateway.sh` 与 Compose。
6. 只有形成可复现的重要性能里程碑才创建带注释 tag；普通实验和失败实验只提交不打 tag。
   建议里程碑使用 `v2.1.0`、`v2.2.0` 等，最终验收发布使用 `v3.0.0`。tag 必须指向已经推送、
   通过门禁且文档完整的 `dev` 提交，不移动、不覆盖。
7. v3.0.0 发布前由验收后的 `dev` 合并到 `main`；实验期间不直接在 `main` 修改。

每个实验建议保留以下产物：

```text
performance-results/<实验ID>/
├── environment.json      代码、tag、依赖、GPU、驱动/CUDA、模型 manifest 摘要
├── dataset.json          音频 ID/SHA256/时长/语言/参考版本，不含敏感正文
├── command.txt           完整启动和压测命令
├── run-01.json           第一轮机器可读结果
├── run-02.json           第二轮机器可读结果
├── run-03.json           第三轮机器可读结果
└── decision.md           中位数、门禁、结论和回滚值
```

压测器现可通过 `--output-json` 原子生成单份 `schema_version=1` 报告，包含环境、输入摘要、
结果、阶段分位数、资源和前后指标快照；最多保留 20 个失败样本的状态、错误、请求 ID、延迟和
分片数，以便关联网关与 vLLM 日志，不保存音频内容。仍可按实验需要拆分为上述目录结构。原始
日志和敏感数据是否入库由数据敏感性和体积决定，至少将去敏摘要与结论写入台账。

## 14. 下一阶段实施顺序

1. 冻结单卡 PyTorch 参数路线：生产默认为 worker=1/batch=32/attention=auto/decode-workers=1/
   predecode=false，batch=1 仅作逐片回滚；不重复已拒绝实验；
2. 先在目标 Linux/CUDA 镜像关闭时间戳，完成当前 vLLM 0.19.1 主 ASR 三轮 ASR-only、API、
   语种、热词、长音频、Tokenizer 与 CER 门禁；失败时回滚部署镜像，不继续架构实验；
3. `PERF-ARCH-001`：在同一 Python 环境使用 ModelScope 固定 revision 本地 Aligner 权重，
   完成 11 语种输出语义对齐和 batch 1/8/16/32 原始吞吐；当前 qwen-asr PyTorch 实现作为基线；
4. 同步执行 `PERF-ALI-001` 拓扑对照：只有目标容器确实可见两张 GPU 时才将候选 Aligner 放到
   `cuda:1`，并分别采集 GPU 0/1 利用率与显存；单 GPU 环境不得伪装成独立 GPU 结果；
5. ARCH-001 达到原始吞吐 +30% 后，接入网关候选 HTTP 路径，执行默认时间戳三轮 2000 请求、
   混合时长、11 语种、时间戳契约、CER 和故障隔离；端到端吞吐至少 +20% 才进入生产设计评审；
6. 只有 ARCH-001 未达门禁且剖析仍显示模型 forward 为主瓶颈时，才启动 `PERF-ARCH-002`
   TensorRT FP16/BF16 导出与独立服务 spike；INT8 另立后续实验；
6. `PERF-BASE-001`、`PERF-LOAD-001` 和观测工作继续作为所有架构对照的证据基础；网关切片、
   scheduler 和协议微调降为次级任务，不与后端架构变量同时改变。

每完成一轮都更新策略状态、台账和下一轮假设。任何收益若不能在相同条件下复现，立即回滚到
实验记录中的基线值，不带入后续实验。当前仓库只记录设计与验收门禁，不安装新版 vLLM、ONNX
或 TensorRT，也不改动稳定 ASR/Aligner 运行路径。
