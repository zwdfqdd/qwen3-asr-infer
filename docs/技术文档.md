# 技术文档（dev，基于 v2.1.0）

## 1. 技术路线

本项目采用“原生 GPU 推理数据面 + 最小 CPU 协议网关”，不在应用层重建模型引擎：

```text
/chinese_asr JSON ─┐
                   ├→ aiohttp 网关 → 解码检查/固定切分/Prompt → vLLM STT API
multipart 音频 ───┘      :8080                         :8081
                                                        ↓
                                     Qwen3-ASR Processor + Scheduler
                                     continuous batching / CUDA Graph
```

选择该路线的原因：vLLM 统一负责 ASR GPU scheduler、continuous batching、KV cache 与 CUDA
Graph；网关不重建 ASR 模型引擎或固定攒批。独立 ForcedAligner 后处理使用专用有界队列和
最大等待窗口动态合并跨请求物理分片，不改变 vLLM 数据面。每张 GPU 只启动一个 vLLM 实例，
多卡通过多实例和上层负载均衡扩容。

## 2. 组件职责

- `src/config.py`：集中读取环境变量、类型转换、范围校验，导出模块级 `settings`。
- `src/sitecustomize.py`：固定依赖兼容层；启用 tokenizer regex 修复，并以进程级可重入锁保护
  Fast Tokenizer 完整公共调用，消除 vLLM Chat/多模态预处理线程共享 Rust tokenizer 时的
  `RuntimeError: Already borrowed` 与上游 HTTP 400，不修改模型文件或请求契约。
- `src/logger.py`：请求 ID 上下文、有界异步队列、严格 JSON、容量受控轮转文件和脱敏摘要。
- `src/gateway.py`：aiohttp 路由、音频检查/切分、热词 Prompt、后端转发、合并与错误契约。
- `src/aligner.py`：默认 Qwen3 ForcedAligner、跨请求有界动态微批、默认关闭的 ASR 重叠
  预解码及 PCM 字节预算、attention 后端观测、单批阶段计时、真实字/词级对齐和按主模型标点
  聚合句级结果；显式后端或预解码失败时拒绝请求，不静默降级。
- `scripts/download_model.py`：纯 urllib ModelScope 下载、SHA256/大小校验、manifest 与文件锁。
- `run.sh`：端口预检、模型准备、vLLM 与网关双进程生命周期管理。
- `tests/test_service.py`：并发、吞吐、延迟、分片和 GPU/CPU 资源压测。
- `tests/verify_qwen_single.py`：两类 API 推理与严格全量参考 CER 门禁。

项目不包含旧 FastAPI/uvicorn 模型层、ASR DynamicBatcher、Transformers 服务后端、Silero VAD
或 CT-Transformer 标点。主模型直接输出标点；ForcedAligner 是默认开启的独立后处理模型，
其有界动态微批只调度 Aligner 物理分片，不接管 vLLM ASR scheduler。

## 3. 音频处理链路

1. `/chinese_asr` 解码 Base64；multipart 接口读取 `file`。两者都执行文件大小保护。
2. libsndfile 读取采样率和真实帧数；零帧或无效容器作为解码失败，不返回空成功。
3. 不超过 32 秒时保留原字节；超过 32 秒时按整数采样帧编码为最长 32 秒 PCM16 WAV。
4. 单个长请求最多并发 3 片，全局最多 96 个长分片在途；所有分片进入同一 vLLM scheduler。
5. `/chinese_asr` 未传 `language` 时，通过同一 vLLM 实例的 Chat Completions 保留模型原始
   `language X<asr_text>文本`，解析为逐物理分片文本和 `slid`；显式语言通过转写端点的
   `to_language` 强制前缀。网关不根据文字、文件名或词表猜测语种。
6. 全部分片成功后按原顺序合并；任一分片失败则整条失败，不返回部分文本。
7. 默认 `/chinese_asr` 按每片实际 `slid` 将音频和文本提交到有界 Aligner 队列。实验性
   预解码开启时，网关在 ASR 阶段以固定 worker 提前生成 PCM，并用队列和全局字节预算限制
   排队及驻留；取消、失败和超预算分片均有明确释放或批内回退路径。Aligner worker 以首条
   任务的固定截止时间动态聚合跨请求物理分片，达到最大 batch 立即调用官方批量 `align()`，再按
   请求和原分片索引拆回真实字/词级结果，并按主模型标点聚合句级结果。队列满时产生背压，不会
   无限增长；取消请求不会取消共享 CUDA 批次，只在完成后丢弃该请求结果。关闭两个时间戳开关后，
   `timestamp` 仅保留物理分片帧边界，`words=[]`。
8. ForcedAligner 只支持 11 种语言。语种为空或不受支持的分片显式跳过对齐：保留 ASR、
   `slid` 和物理边界，`words=[]`，顶层 `message` 记录分片索引及语种；其他支持分片仍对齐。
9. 只有全部非空分片均成功对齐时，句级模式才使用主模型标点聚合 Aligner 单元；跨语种句子
   的 `slid` 按首次出现顺序以逗号合并。存在跳过分片时整条响应保留物理分片结构并告警，
   防止把未对齐分片边界描述成句级时间戳。`X-Audio-Chunks` 始终是物理分片数。
10. 请求日志中间件在生产线程固化 `X-Request-ID`，并维护固定的请求阶段计时。JSON/multipart
    解析、Base64 解码、切片、单请求/全局分片排队、后端 HTTP、ASR 墙钟、Aligner 排队/推理、
    后处理和序列化耗时通过同一 `stage_timings_ms` 写入完成日志，并以 `Server-Timing` 返回；
    分片排队和后端耗时为累计值，不能与 `total` 相加。监听线程负责严格 JSON 格式化和
    stdout/文件 I/O，避免日志背压阻塞 aiohttp。日志保留白名单路由/媒体类型、字段名、音频
    统计、分片/语言/结果计数、错误码、状态和耗时摘要；`/chinese_asr` 同时记录有界
    `input_json` 和 `result_json`，其中输入 Base64 只保留前 64 个 ASCII 字节。热词、来源 URL
    和识别正文会进入业务 JSON；音频二进制、multipart 文件名和后端 Prompt 仍不落日志。
    取消和客户端断连按观测状态 499 区分于服务端 5xx；退出时排空队列。
11. 网关到 vLLM 使用单个长生命周期 `ClientSession` 和显式 `TCPConnector`；连接总数与单主机
    上限默认均为 100，客户端空闲连接默认保留 4 秒。该值短于后端关闭窗口，用于避免复用已被
    vLLM 关闭的连接；连接断开日志保留底层 aiohttp 异常类型和 errno，不自动重试 POST。
12. `tests/test_service.py` 解析固定 `Server-Timing`，生成端到端及逐阶段分位数，并可原子写入
    机器可读 JSON；报告包含去敏环境、输入 SHA256、资源统计和压测前后 vLLM 指标快照，为
    后续 Aligner、连接池、切片和 scheduler 实验提供同格式证据。
13. 文件日志固定为 `gateway.log`，按单文件大小和备份数建立硬容量上限，启动时再按天数清理
    过期备份和旧 PID 日志。`run.sh` 将网关 JSON 独占 stdout，启动脚本、下载器和 vLLM 使用
    stderr；Docker 对两条流实施独立于应用文件的 `json-file` 容量轮转。

当前是硬切，无 VAD、重叠和跨段去重。长音频推荐 WAV/FLAC/OGG；其他格式取决于系统
libsndfile 编译能力。默认 7500 秒时长上限与 229 MiB 音频、308 MiB 请求体限制分别保护
不同阶段；两个字节上限由 7500 秒 16 kHz 单声道 PCM16 WAV 及其 Base64 膨胀推导，改动时长
必须同步重算。7500 秒按 32 秒分片约 235 片，单请求墙钟与网关 RSS 显著上升，需实测确认。
单 A10 默认时间戳模式是
vLLM 与网关 Aligner 两个 CUDA 进程，不是同进程双模型；默认 `cuda:0/bfloat16/1/1`，vLLM
显存预算固定默认 0.85，必须在目标机验证 OOM 和尾延迟。
官方流式能力尚未接入当前 HTTP 网关；Qwen3-ASR/ForcedAligner 均不提供说话人识别。
## 4. 当前过渡架构与后续 Aligner 迁移

当前单 Python 环境统一到 `vllm[audio]==0.19.1`，只迁移了主 ASR 数据面；默认时间戳仍由网关
进程内的 `qwen-asr==0.0.6` PyTorch ForcedAligner 提供：

```text
当前镜像：一套 site-packages（vLLM 0.19.1 + Transformers 4.57.6 + qwen-asr 0.0.6）
基础镜像必须为 CUDA 12.9 构建（宿主驱动 535 不支持 CUDA 13.0）

客户端 → aiohttp :8080 → Qwen3-ASR vLLM 0.19.1 :8081
                    └→ 网关内 PyTorch ForcedAligner → 时间戳校验/句级聚合
```

版本上限由部署硬件决定而不是功能取舍：vLLM 0.20 起默认绑定 PyTorch 2.11 + CUDA 13.0，需要
580 以上驱动；目标 A10 宿主驱动为 535，因此固定在最后一个默认 CUDA 12.9 的 0.19.1。同一
解释器内不得混装第二个 vLLM 或 CUDA 13 运行时。Transformers v4 是 qwen-asr 0.0.6 的必要
兼容；在 Aligner 完成迁移和全部 CER/并发门禁前不得升级到 5.x。`src/sitecustomize.py` 的
tokenizer regex 与并发锁继续保留，待目标环境重新验收后再按证据处理。

`PERF-ARCH-001` 的后续目标仅是把 ForcedAligner 从 PyTorch 改为 vLLM
pooling/token-classification。该模型由音频塔、Qwen3 骨干和分类头在 `<timestamp>` token 位置
预测时间桶；目前只有独立 spike，尚未接入 `src/aligner.py`、网关或生产启动脚本。候选拓扑为：

```text
客户端 → aiohttp :8080
           ├→ Qwen3-ASR vLLM 0.19.1 :8081
           └→ Qwen3 ForcedAligner token-classify 0.19.1 :独立端口
                    ↓
      CPU 时间戳后处理/边界校验/句级聚合 → 原业务响应
```

ASR 与候选 Aligner 可使用同一个解释器和同一 vLLM 版本，但仍是两个模型进程；多 GPU 时每卡
一个 vLLM。单 GPU 上启动两个 vLLM 会违反当前每卡一个 vLLM 约定，不作为首轮目标拓扑。
候选必须逐语言验证等价的 CPU 分词、`parse_timestamp()`、单调性和边界，不得伪造或静默降级。
参考 [vLLM Token Classification 用法](https://docs.vllm.ai/en/v0.19.0/models/pooling_models/token_classify/)和
[Qwen3 ForcedAligner 模型文档](https://docs.vllm.ai/en/v0.19.0/api/vllm/model_executor/models/qwen3_asr_forced_aligner/)；
外部资料内容均为转述，不能据此宣称当前服务已经集成 token-classify。

TensorRT 仍是后续条件实验，不与当前运行环境混装；只有 token-classify Aligner 未达架构门禁
时，才在另一个候选镜像中启动 FP16/BF16 导出验证。
