### PERF-ARCH-001 Phase A 首轮对照 7/11 未通过：分歧是桶级 argmax，非浮点噪声

- `oracle` 11/11；`compare` **7/11**。未通过：Cantonese 80 ms、French 80 ms、Spanish 80 ms、
  Korean 400 ms；通过的 7 种为精确 0.000 ms。**全部偏差都是 80 ms 桶宽的整数倍**，说明是离散桶
  argmax 分歧，不是浮点误差。两侧内核栈不同（sdpa 对 FLASH_ATTN + norm_quant/act_quant 融合），
  bfloat16 下桶边界近似平局是合理嫌疑，但首轮数据不足以证实。
- **离线证实 `fix_timestamp` 强不连续**：取最长非降子序列后插值，单个 ±1 桶翻转可改变被选子序列。
  实例 `[3,30,28,0,0,23,20]` 仅第 3 位 0→1，修复后逐项差达 2400 ms（30 个桶宽）。因此 Korean 的
  400 ms 与单处近似平局完全相容，不能据此认为它比另外三种更严重。
- 方法论更正：**修复后时间戳不是衡量后端等价性的稳定指标**，比较对象经过了不连续函数。等价性应先
  比较修复前原始桶下标，再判断分歧位置是否为近似平局。
- 工具据此扩展，**未放宽任何门禁**，`--timestamp-tolerance-ms` 仍为 1 ms：`oracle` 复用 ALI-011
  已验证的官方分解记录 argmax 原始桶，并要求复刻单元与官方 `align()` 零容差一致，否则失败，避免
  产出可疑诊断；`compare` 记录 vLLM 原始桶、全量超限位置、桶级差异与分歧位置 top1-top2 logit 间距，
  按"桶完全一致 / 近似平局 / 真实分歧"三类分别提示。`_compare_units` 改为全量收集容差超限而非首错
  中断，结构性不一致（文本、数量）仍立即抛错。
- **Phase A 判定为未通过**，Phase C 不启动。

### PERF-ARCH-001 Phase A 第三轮：双侧候选证明 BF16 非整体近似平局，转 FP16 单变量

- 第三轮原始桶结果与第二轮完全复现。Cantonese 的相邻桶 119/118 互为 top-5，但两侧间距为
  0.20808/0.1875；Korean 位置 1 的桶 21/16 互为 top-5，两侧间距 0.16494/0.4375，差 5 桶；
  两例都不能归为近似平局。Spanish 为相邻桶且 vLLM 侧平局，可归为数值敏感位置。
- French 10 个分歧位置成因混合：3 处相邻桶近似平局、1 处两侧近似平局、3 处互为候选但间距不小、
  3 处对侧答案未进入 top-5；最大仍差 32 桶。不存在一个可合理整体豁免的“80 ms 边界误差”模型。
- 定案：**BF16 vLLM token-classify 路径不满足 1 ms Phase A 门禁**。7 种逐桶精确一致且失败模式
  稳定复现，排除 tokenizer/processor/桶换算错误和随机抖动；差异更符合不同低精度内核栈改变特定
  位置候选排序，但尚未分离 attention 与融合算子贡献。
- 下一步遵守单变量纪律：固定生产 PyTorch BF16 oracle，只把 vLLM candidate dtype 改为 FP16。
  A10 支持 FP16，且 FP16 尾数 10 bit 高于 BF16 的 7 bit；不同时修改 oracle、attention、融合、

### 新增 PERF-ALI-011 拆分计时 spike（只测量不优化）

- 新增 `experiments/perf_ali_011/spike.py` 与 README，把官方 `align()` 按 qwen-asr 0.0.6

  `aligner_batch_model_call_ms` 包裹整个 `align()` 调用，把 CPU 分词、mel 特征提取、GPU 前向

- 拆到七段而非简单区分 CPU/GPU 的原因：两个 CPU 段都是候选主体且优化手段完全不同。

  `staged_overhead_percent` 量化计时点自身开销。
- 复刻有意省略官方三处入参护栏（`ensure_list()`、语种广播、batch 长度检查），均为常数级判断；

- 稳定性守卫沿用 ALI-010 的 `_STABILITY_LIMIT=1.2`，但只对均值达到 1 ms 的段判定——亚毫秒段
  本身极差比就大，全部告警会淹没真正不稳的段。默认 `--warmup 15 --iterations 30`。
- 无 GPU 静态校验通过：极差比计算、稳定性判定三种情形、结果一致性四类差异全部被拦截、
  batch 非法值拦截、七段常量与实际计时段一致、AST 契约检查。临时校验脚本执行后已删除。
- 已知边界：本轮同一音频填满 batch，批内等长因此无 padding 浪费，真实混合长度下 CPU 占比会
  更高，实测值是偏乐观下界；只覆盖中文，日语 `nagisa` 与韩语 `soynlp` 分词成本需另测。

### ForcedAligner torch.compile 实测拒绝，派生 CPU 特征提取新靶点

- `PERF-ALI-010` 判定拒绝。thinker 前向 670.05→559.62 ms（+16.48%）达标，但生产口径
  `align()` 只有 926.41→868.02 ms（+6.30%），未达 15% 晋级线。编译前后对齐单元文本与时间戳
  逐项一致（容差 1 ms），无 NaN、OOM 或崩溃，属收益不足而非实现失败。
- 全部逻辑位于 `experiments/perf_ali_010/spike.py`，只在实验进程内包装
  `aligner.model.thinker`。**`src/aligner.py` 与生产默认路径未做任何改动。**
- 首轮数据作废并加固 spike：默认 `--warmup 5` 时 batch=32 的 eager `align` 极差达 2.3 倍
  （min 836.70 / max 1939.73），均值虚高使收益假报为 +47.40%。定位手段是用 `align - thinker`
  反推纯 CPU 部分——batch=1/8 两次测量都接近，唯 batch=32 差 570 ms，而编译不可能改变 CPU 前后
  处理，因此差异来自测量本身。提到 `--warmup 15 --iterations 30` 后收益落到真实的 +6.30%。
- 加固内容：`_stats()` 增加 `max_over_min` 极差比字段，新增 `_STABILITY_LIMIT=1.2` 与
  `_unstable()`，超限即写入报告 `measurement_unstable` 并打印警告说明该组数据不得用于判定；
  报告新增 `dynamo_graphs_added`、`cpu_eager_ms`、`cpu_compiled_ms`。默认预热与迭代次数上调。
- 通用教训：**编译类实验必须先证明 eager 基线稳定再谈收益**，分母不稳时误差方向恰好使收益
  偏大，容易误判达标。
- 副产品一（价值高于本实验结论）：batch=32 时 `align()` 有约 256 ms（约 28%）在 CPU 上，
  主要是 processor 的 mel 特征提取。此前未被识别，因为 `aligner_batch_audio_decode_ms`
  （146.93 ms）只统计 WAV 解码，特征提取被并入 `aligner_batch_model_call_ms`——即 780 ms 的
  “模型调用”约三分之一不在 GPU 上。已立 `PERF-ALI-011`，第一步是补拆分计时而非直接优化。
- 副产品二：`dynamo_graphs` 为 `-1→8`（batch=1 首编译 8 处图断裂）、`8→12`（batch 1→8 新增
  4 个图，即批大小变化触发重编译）、`12→12`。生产动态微批批大小 1～32 浮动会反复重编译，
  代价未量化；重启编译路线前须先用 `--compile-dynamic` 单变量验证。
- 未测的后续单变量：`--compile-mode reduce-overhead`、`--compile-dynamic`、`--dtype float16`。
  但它们只影响 thinker 的 670 ms，CPU 的 256 ms 不受编译影响，`align()` 收益上限被 CPU 锁死，
  因此优先做 `PERF-ALI-011`。

### 分片级对齐流水实测拒绝

- `PERF-ALI-009` 判定拒绝。并发 96/4/1 三个点分别为 -1.52%/+0.84%/+5.26%，并发越低越差；
  成功率与 `Server-Timing` 覆盖率均 100%。`ALIGNER_PIPELINE_ENABLED` 保留但默认关闭，
  文档标注不建议开启。
- 根因经批次统计证实：流水使分片陆续到达，5 ms 固定合批窗口只能聚合到少量分片。并发 1 时
  6 个有效分片被切成 4 批、平均 1.5 个一批（批量模式为 1 批 6 个），对齐阶段从 130.90 ms 升到
  307.50 ms，多出的约 176 ms 超过重叠所能节省的时间。
- 结论：“尽早提交”与“攒够再跑”方向相反，无法通过调 `ALIGNER_BATCH_WAIT_MS` 折中——等到分片
  全部到齐即退化为批量模式。因此不再做 wait 窗口的二次调参。
- 功能实现本身正确：两种模式时间戳逐项一致，五项语义校验全过。仅在 Aligner 迁移到由 vLLM
  调度器管理合批的实现后才需重新实测本项。

### 新增分片级对齐流水（默认关闭）

- 新增 `ALIGNER_PIPELINE_ENABLED`（默认 false）。原链路为请求级串行：先等整条请求全部分片
  完成 ASR，再整体提交对齐。开启后每个分片 ASR 完成即提交对齐，两个阶段重叠。10 秒单分片
  场景无差别，7500 秒上限对应约 235 个分片时才体现结构性收益。
- 实现方式为最小侵入：`_recognize_chunks` 新增 `on_chunk_ready` 回调，在分片并发槽位释放后
  触发；`ForcedAlignerEngine.start_pipeline()` 返回按分片提交的流水对象。入队与跨请求合批
  语义与批量接口完全一致，只是提交时机提前，因此单分片请求两种模式等价。
- 指标语义变化：流水模式下 `aligner_latency_ms` 覆盖“首个分片提交到全部对齐完成”，与 ASR
  时间部分重叠；`aligner-queue` 取各分片排队等待的最坏值。日志新增 `aligner_pipeline` 字段，
  性能报告环境白名单同步登记 `ALIGNER_PIPELINE_ENABLED` 与 `ENABLE_MPS`。
- 无 GPU 语义校验覆盖：乱序完成的分片按原索引归位、空文本与不支持语种跳过行为不变、同一分片
  重复提交显式报错、整批失败向调用方抛出且不残留未完成任务、请求取消只取消自身任务。
- 未验证项：目标机多分片端到端收益与显存表现。仓库无可复现长音频标准集，可临时调低
  `AUDIO_CHUNK_SECONDS` 让 30 秒音频切成多片进行对照。

### 生产默认值调整：Aligner 批大小与可选 MPS

- `ALIGNER_BATCH_SIZE` 默认由 1 改为 32，`run.sh`、`run_gateway.sh`、`src/config.py` 与
  `docker-compose.yml` 四处同步。依据目标 A10 实测：端到端由 107.33 升至 228.57 audio_s/s
  （+113%），显存峰值约 20315 MiB，A10 余量约 2.7 GiB。设为 1 仍可逐片回滚。
- 新增 `ENABLE_MPS`（默认 false）及 `CUDA_MPS_PIPE_DIRECTORY`、`CUDA_MPS_LOG_DIRECTORY`。
  `run.sh` 会主动把控制守护进程调整到与开关一致：true 时不在线则启动并等待就绪，已在线则
  复用；false 时在线且无活跃客户端则停止。vLLM 就绪后在 true 下再校验一次 MPS server 是否
  已创建，未创建即退出。
- 主动管理而非仅校验的原因：实测发现仅靠环境变量无法决定是否走 MPS。即使开关为 false，只要
  守护进程在运行，两个 CUDA 进程仍以 `M+C` 方式接入；未设置 `CUDA_MPS_PIPE_DIRECTORY` 时
  运行时还会查默认 `/tmp/nvidia-mps`。守护进程缺失时服务同样可正常启动、全部健康指标正常，
  但吞吐静默下降约 17.8%。静默降级与对称的“静默启用”都会污染性能基线。
- 接入判据为“是否存在 MPS server”，因为 server 由首个客户端接入时创建、最后一个客户端退出后
  消失，比解析客户端列表稳定；但若 server 由其他进程创建仍可能误判通过，发布须人工核对
  `nvidia-smi` 中 `Type` 为 `M+C`。
- 目标机回归：四条状态转换路径全部通过，其中 `ENABLE_MPS=false` 且存在活跃客户端时正确拒绝
  启动而未强行停止守护进程。两条运行路径各一轮 2000 请求均 100% 成功、`Server-Timing`
  覆盖率 100%：`true` 为 271.45 audio_s/s（对照中位 274.22，-1.0%），`false` 为 225.19
  （对照中位 228.57，-1.5%）。生产默认保持 `ENABLE_MPS=false`。
- 安全边界：守护进程可能被本机其他 CUDA 进程共用，因此 `ENABLE_MPS=false` 且存在活跃客户端
  时直接拒绝启动，不强行停止。活跃判据为“是否存在 MPS server”，因为 server 由首个客户端接入
  时创建、最后一个客户端退出后消失，比解析 `get_device_client_list` 的非结构化输出可靠。
- `quit` 在仍有客户端连接时会无限等待，因此停止操作带 30 秒超时兜底，缺少 `timeout` 命令时
  拒绝启动。状态调整安排在端口等快速失败校验之后，避免因这些校验退出而遗留不一致状态。
  `run.sh` 退出时不会自动恢复守护进程状态。
- `run_gateway.sh` 作为调试入口不主动改变守护进程状态，避免与并行的 `run.sh` 抢管理权，
  仅在实际状态与 `ENABLE_MPS` 不一致时拒绝启动。
- 同时修复 `docker-compose.yml` 的遗漏：`MAX_AUDIO_SECONDS` 由 2000 更新为 7500，
  `MAX_UPLOAD_MB` 由 280 更新为 229，`MAX_JSON_BODY_MB` 由 280 更新为 308，与其余入口一致。

### MPS 故障验证完成并记录静默降级阻塞项

- 目标 A10 完成四项故障场景验证：网关退出、网关单独重启、`quit` 优雅退出、daemon 被

### 时间戳技术路线定稿并暂停对齐后端替换

- 结论：继续使用 Qwen3-ForcedAligner。主模型为自回归解码，输出 token 数与音频帧数无对应
  关系，无法按 CTC 方式从帧索引反推时间戳；ForcedAligner 以分类头预测 80 ms 时间桶，时间
  分辨率与帧同步方案相同，自研对齐无精度优势。外部 CTC 路线因 `torchaudio` 对齐 API 已弃用
  及依赖约束冲突不予采用。禁止用 VAD 或分片边界伪造字级时间戳。
- 保留路线与优先级写入 [性能调优](性能调优.md) 11.5/11.6 和性能实验台账：生产默认值
  （batch=32 + MPS）、按需对齐、分片级流水、降低对齐粒度、token-classify 集成、独立 GPU
  拓扑、TensorRT。本次仅记录决策，不改动运行代码与生产默认值。
- 已实测支撑：0.19.1 环境 Aligner batch=1 为 107.33、batch=32 为 228.57、叠加 MPS 为
  274.22 audio_s/s；token-classify 原始吞吐 1180.51，同口径相对 PyTorch 409.8 为 +188.1%。

### ForcedAligner 跨请求有界动态微批

- 将请求级 Aligner 信号量改为显式启动/关闭的有界物理分片队列；worker 从首条任务到达起按
  固定最大等待窗口动态聚合，达到 `ALIGNER_BATCH_SIZE` 立即调用官方批量 `align()`，并按请求
  与物理分片原索引拆回真实时间戳。
- 新增 `ALIGNER_BATCH_WAIT_MS` 和 `ALIGNER_QUEUE_SIZE`；`ALIGNER_CONCURRENCY` 表示共享模型
  worker 数，`ALIGNER_BATCH_SIZE=1` 保留逐片回滚。取消请求不会取消共享 CUDA 批次，完成后
  丢弃对应结果；单批异常广播给该批存活请求，队列和 worker 在网关退出时有序关闭。
- `aligner_completed` 与请求完成日志新增实际 batch 数、最大/平均 batch 和提交时最大队列深度；
  `aligner-queue` 表示提交到首批开始，`aligner` 表示首批开始到该请求全部分片完成的墙钟时间。
- 无 GPU 调度冒烟确认实际合批、批失败恢复、单请求取消隔离和满队列优雅关闭。目标 A10
  batch=32 性能诊断轮达到 220.03 audio_s/s、P95 4641.8 ms、P99 5585.0 ms，当前是最佳平衡
  候选。batch=48 达到 228.99 audio_s/s，但相对 batch=32 吞吐仅 +4.1%、P95 +4.9%、P99
  +1.1%，显存再增加 968 MiB 至 21821 MiB，未达到晋级线并拒绝继续放大 batch。两轮均尚缺
  实际 batch size 与错误检索日志。固定 batch=32 后，worker=2 达到 228.22 audio_s/s，相对
  worker=1 仅 +3.7%，而 Aligner 执行墙钟增加 91.3%，拒绝共享模型并发及更高 worker。
- 新增 `ALIGNER_ATTENTION_BACKEND=auto/eager/sdpa/flash_attention_2`：默认 `auto` 不覆盖
  Transformers 自动选择；显式后端直接传给官方模型，不兼容时启动失败，不静默回退。启动日志
  记录配置值和模型最终实际后端，性能 JSON 环境白名单同步记录配置值；启动脚本会在启动 vLLM
  前预检显式 FA2 所需的 `flash_attn` 模块。
- 目标镜像 `auto` 最终实际使用 `sdpa`；显式 FA2 因未安装 `flash_attn` 启动失败。不临时安装
  或放宽依赖，该路径当前阻塞，保留 attention=auto。
- 新增 Aligner 单批内部阶段计时：按请求参与的唯一共享批次汇总 WAV 解码、官方
  `model.align()` 完整调用和结果构建耗时，写入 `aligner_completed` 与请求完成日志，不改变
  业务响应或固定 14 项 `Server-Timing`。目标 A10 worker=1/batch=32 诊断达到 1000/1000、
  218.95 audio_s/s；三项均值为 281.12/1097.04/7.53 ms，占合计约 20.3%/79.2%/0.5%。
- 新增 `ALIGNER_DECODE_WORKERS` 和持久化固定大小线程池，只并行独立内存 WAV 解码并保持批次
  顺序，关闭时有序回收；默认 1 保留原串行路径。worker=1/batch=32/attention=auto 下仅测试
  decode-workers=4，达到 1000/1000、221.89 audio_s/s；解码均值从 281.12 降至 254.36 ms
  （-9.52%），模型调用从 1097.04 升至 1105.92 ms（+0.81%），最终吞吐仅 +1.34%、P95
  -2.31%，未达到晋级线。该路线已拒绝并恢复 1，不继续测试其他线程数。
- 新增默认关闭的 `ALIGNER_PREDECODE_ENABLED`：在 ASR 阶段通过有界单 worker 队列提前解码，
  `ALIGNER_PREDECODE_MAX_MB=128` 以加权预算同时限制排队及已解码 PCM 驻留。Aligner 批次优先
  消费预解码数据；单片超过预算时保留原批内解码。ASR 失败、取消、无效音频和退出均清理 Future
  与预算，预解码错误不静默降级；日志新增残余等待、预解码 CPU 耗时和命中分片数。
- 无 GPU 冒烟覆盖 ASR 重叠、batch=4、预算归零、提前退出、解码失败恢复、超预算回退和关闭
  排空。目标 A10 开启后达到 1000/1000、222.98 audio_s/s；预解码命中 100%、残余等待 0.01 ms、
  批内解码 0.03 ms，但 `model.align()` 因同卡重叠从 1097.04 增至 1351.02 ms（+23.15%），
  最终吞吐仅 +1.84%、P95 -1.58%，未达到门禁。该路线拒绝并恢复默认关闭；官方 `align()` 已有
  `torch.inference_mode()`，单卡软件优化转入独立 Aligner GPU/实例拓扑，不再扩大调度参数。

### Fast Tokenizer 并发稳定性

- 定位 ASR-only 并发失败根因：vLLM 0.16.0 的 Chat/多模态预处理线程并发调用同一个
  Transformers 4.57.6 Fast Tokenizer，在 `enable_truncation` 修改 Rust tokenizer 状态时触发
  `RuntimeError: Already borrowed`，vLLM 返回 HTTP 400；不是 GPU OOM、模型推理、Aligner、
  客户端超时或连接池问题。
- `src/sitecustomize.py` 使用进程级可重入锁覆盖 `PreTrainedTokenizerFast.__call__` 的完整调用
  生命周期，保留 Fast Tokenizer、依赖版本、客户端并发和 vLLM scheduler，不重试 POST。
- 目标 GPU 针对性验证 2000/2000；正式 ASR-only 三轮累计 6000/6000，`Server-Timing` 覆盖率
  100%，`Already borrowed` 和上游 HTTP 400 均为零。三轮中位数为 114.18 QPS、1141.75
  audio_s/s、平均延迟 824.0 ms、P95 1055.5 ms、P99 1606.0 ms。
- 修复前失败轮和诊断报告不作为性能基线；正式报告仅保留修复后的三轮结果。

- Dockerfile 兼容仅提供 `python3`/`python3.12` 的 vLLM 基础镜像：构建时探测实际解释器并

- 为私有基础镜像预装但依赖不完整的 PyGObject 补齐系统包 `python3-cairo`，继续保留严格

- 统一默认 `AUDIO_CHUNK_SECONDS=32`、`MAX_AUDIO_SECONDS=2000`、`MAX_UPLOAD_MB=280`、

- `CHUNK_CONCURRENCY=3`、`LONG_CHUNKS_IN_FLIGHT=96`；采用历史 A10 纯 90 秒最高吞吐组合，

- 统一 vLLM 默认：`VLLM_GPU_MEMORY_UTILIZATION=0.85`、`VLLM_MAX_MODEL_LEN=10240`、
  `VLLM_MAX_NUM_BATCHED_TOKENS=10240`、`VLLM_MAX_AUDIO_CLIP_FILESIZE_MB=96`、
  `VLLM_LOAD_FORMAT=safetensors`。

### 语种识别与 ForcedAligner

- `/chinese_asr` 未传 `language` 时保留 Qwen3-ASR 原始自动检测标签，为每个物理分片填写
  `slid`；显式语言支持官方 30 种语言名称或 ISO 代码，不根据文字或文件名猜测。
- 主模型官方能力范围为 30 种语言和 22 种中国方言/口音；方言标签可自动返回，但不承诺
  对全部相近方言做到客观准确区分。
- 新增并默认启用 `Qwen/Qwen3-ForcedAligner-0.6B`，仅从 ModelScope 固定 revision 下载；
  支持 `/chinese_asr` 中文字符/其他语言词级时间戳及按主模型标点聚合的句级结果。
- ForcedAligner 只支持 Chinese、English、Cantonese、French、German、Italian、Japanese、
  Korean、Portuguese、Russian、Spanish。语种为空或不受支持的分片显式跳过对齐但不中断
  ASR：HTTP 200 保留文本、`slid` 和物理边界，`words=[]`，顶层 `message` 列出跳过项；支持
  的其他分片仍执行真实对齐。取消 `DEFAULT_ALIGNER_LANGUAGE=Chinese`，不静默回退中文。
- 全部分片成功对齐时，句级结果继承实际对齐单元语言，跨语种句子的 `slid` 按出现顺序以
  逗号合并；存在跳过分片时禁用句级聚合并显式告警，防止伪造句级时间戳。
- 错误码 1009 保留给 Aligner 推理失败、返回结构异常或句级结果无法可靠映射，不再用于可预判
  的不支持语种。
- 单 A10 同卡默认 `cuda:0/bfloat16/concurrency=1/batch=1`；vLLM 固定默认显存预算为 0.85。
  该能力尚需目标 Linux/CUDA 的 OOM、吞吐和尾延迟验收。
- 主模型自带标点，不使用 CT-Transformer；流式 HTTP 网关和说话人识别仍未实现。
