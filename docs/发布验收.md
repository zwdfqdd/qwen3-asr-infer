### 日志验收

1. 网关 logger 写入 stdout 和轮转文件的每一行都必须是严格可解析 JSON，并包含 `event`、
   `request_id` 和日志级别；NaN、Infinity、未知对象和二进制字段必须安全降级。通过 `run.sh`
   启动时，容器 stdout 仅承载网关 JSON；启动提示、下载器、vLLM 和 Python 警告位于 stderr。
   `docker compose logs` 可合并展示，但日志采集器必须保留并利用 stream 元数据。
2. 成功、4xx、5xx 和观测状态 499 的 `http_request_completed` 必须保留 `input_fields`、
   `output_fields`、`outcome`、HTTP 状态和总耗时等统计摘要；业务请求还应包含音频大小/时长、
   分片数、语言模式和结果统计或错误码。`/chinese_asr` 成功及业务错误日志还必须包含
   `input_json`、`result_json`；代理错误必须包含上游状态或明确错误码。
3. 使用唯一 ASCII 哨兵构造超过 64 字节的 Base64：`input_json.base64` 必须与原值前 64 字节
   完全一致，第 65 字节及后续内容在 stdout、轮转文件和异常日志中必须零命中，同时
   `base64_encoded_chars` 保留完整字符数。验证热词、`article_url`、语言和模拟识别文本进入
   对应业务 JSON；音频二进制、multipart 文件名和后端 Prompt 仍须零命中。覆盖 CRLF、Unicode
   格式控制符、超长字符串、超长数组、NaN/Infinity 和不可序列化对象，确认超限内容有明确
   截断标记且每一行仍是严格 JSON。
4. 以小队列和慢输出验证请求线程不等待 I/O、`dropped_logs_before` 可观测且关闭能够排空；
   强制触发文件大小轮转、不同 PID 重启、旧 PID 日志过期清理、目录不可写和运行期写入失败。
   `gateway.log` 加备份的总大小不得超过配置上限，失败时 stdout 应继续工作且不打印内部 traceback。
5. 验证 stdout、ELK 和 `asr-logs` 卷的读取权限及保留周期；按 `X-Request-ID` 能关联请求、
   后端分片和 Aligner。未处理异常应包含受限堆栈，但不得在异常消息中拼接请求正文。

## 6. 性能门禁

按 [性能调优文档](性能调优.md) 在目标 Linux/CUDA 环境至少执行短音频和业务最长音频：

```bash
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_10s.wav --concurrency 96 --total 2000 \
  --require-server-timing \
  --output-json performance-results/PERF-BASE-001-short-run-01.json
```

每种条件至少执行三轮并保存独立 JSON。报告必须是严格 JSON，`Server-Timing` 覆盖率为 100%，
14 个固定阶段都有有限非负分位数；确认 `chunk-local/global-queue` 和 `asr-backend` 按累计值
解释，`asr`/`total` 按墙钟解释。正式报告应包含输入 SHA256、Git 提交、目标 GPU 资源采样及
压测前后 vLLM 指标；指标抓取失败必须作为验收缺口处理，不能仅凭终端文本发布。失败响应
必须在 `results.failure_samples` 中保存有限数量的 HTTP 状态、错误、`X-Request-ID`、延迟和
分片数，用于关联网关与 vLLM 日志；不得记录音频内容或以遗漏失败样本掩盖稳定性问题。

发布标准应明确：成功率、P95/P99、audio_s/s、GPU 显存峰值和 CER。v1.0.0 发布默认
`3/64`；当前工作区统一为 `3/96`、32 秒分片、最大 7500 秒，并默认启用同卡 ForcedAligner；
必须与 64/128 做同条件混合时长回放，确认显存和尾延迟可接受。

### Fast Tokenizer 并发稳定性门禁

历史 vLLM 0.16.0 与 Transformers 4.57.6 组合需要 `src/sitecustomize.py` 的共享 Fast
Tokenizer 进程级调用锁；迁移到 vLLM 0.19.1 后暂时保留该兼容层，必须通过本节门禁后才能
评估移除。镜像内先确认兼容层生效：

```bash
PYTHONPATH="$PWD/src" python -c \
'import sitecustomize; from transformers.tokenization_utils_fast import PreTrainedTokenizerFast; print(sitecustomize.__file__, hasattr(PreTrainedTokenizerFast.__call__, "__wrapped__"))'
```

输出必须指向当前项目 `src/sitecustomize.py` 且末项为 `True`。关闭两个时间戳开关后，以
`/chinese_asr` 自动语种、10 秒音频、并发 96、每轮 2000 请求执行三轮；每轮必须 2000/2000，
`Server-Timing` 覆盖率 100%，并确认 vLLM stderr 中 `RuntimeError: Already borrowed`、网关
`backend_chunk_failed.upstream_status=400` 均为零。当前目标 GPU 正式三轮累计 6000/6000，
中位数为 114.18 QPS、1141.75 audio_s/s、平均延迟 824.0 ms、P95 1055.5 ms、P99
1606.0 ms。删除该锁、切换 tokenizer 实现、升级依赖或降低并发都属于新变量，必须重新验收。

### ForcedAligner 跨请求动态微批门禁

动态微批使用物理分片有界队列；`ALIGNER_BATCH_SIZE=1` 是逐片回滚路径。首轮目标 GPU 对照
固定 `ALIGNER_CONCURRENCY=1`、`ALIGNER_QUEUE_SIZE=256`、`ALIGNER_BATCH_WAIT_MS=5`，仅将
`ALIGNER_BATCH_SIZE` 依次设为 1/2/4/8/16/32/48。batch=32 达到 220.03 audio_s/s、P95
4641.8 ms、P99 5585.0 ms 和 20853 MiB 显存峰值；batch=48 仅提升到 228.99 audio_s/s，
同时 P95 升至 4868.7 ms、显存升至 21821 MiB，因增益不足 5% 被拒绝。当前候选恢复 batch=32；
worker=2 在 batch=32 下也仅提升 3.7% 吞吐、执行墙钟增加 91.3%，被拒绝。attention=auto
已确认实际为 SDPA；当前固定镜像缺少 `flash_attn`，显式 FA2 阻塞。当前候选为
worker=1/batch=32/attention=auto；候选配置至少执行三轮 2000 请求并保存独立 JSON，日志中的
`aligner_batch_size_max/mean` 必须证明实际跨请求合批，且应保留
`aligner_batch_audio_decode_ms`、`aligner_batch_model_call_ms`、
`aligner_batch_result_build_ms` 以解释单批瓶颈，不能仅凭吞吐推断。阶段诊断已测得三项均值
281.12/1097.04/7.53 ms，解码占合计约 20.3%。固定其余参数的
`ALIGNER_DECODE_WORKERS=4` 首轮达到 1000/1000、221.89 audio_s/s、P95 4653.3 ms、P99
5285.0 ms；解码从 281.12 降至 254.36 ms（-9.52%），模型调用从 1097.04 升至 1105.92 ms
（+0.81%），最终吞吐仅 +1.34%、P95 -2.31%，未达到性能门禁。该路线拒绝，生产和候选均恢复
`ALIGNER_DECODE_WORKERS=1`；不得凭单轮 P99 改默认值，也不继续测试其他线程数。

预解码目标 A10 单变量结果为 1000/1000、222.98 audio_s/s、P95 4688.2 ms、P99
5577.6 ms；命中率 100%、残余等待 0.01 ms、批内解码 0.03 ms，但 `model.align()` 因同卡
重叠从 1097.04 增至 1351.02 ms（+23.15%），最终吞吐仅 +1.84%、P95 -1.58%。该路线拒绝，
恢复 `ALIGNER_PREDECODE_ENABLED=false`；不得扩大 worker、内存预算或队列继续试探。官方
`align()` 已有 `torch.inference_mode()`，下一性能验收必须改为独立 Aligner GPU/实例拓扑，
不能把增加一张 GPU 的结果描述为单 GPU 软件收益。

验收还必须覆盖：低流量最多增加配置的等待窗口；队列背压不无限增长；客户端取消后 worker
继续服务且不返回错配结果；单批模型异常向该批所有请求返回 1009 而不杀死后续 worker；SIGTERM
在 Compose 的 2 分钟窗口内排空已接受任务；长短音频混合时短请求 P99 不明显退化。每个配置均
执行时间戳单调性、部分不支持语种契约和全量 CER。任何 OOM、结果串号、Future 泄漏、worker
挂死或静默降级均为不通过。

## 7. 上线步骤

1. 从 `v2.1.0` tag 构建不可变镜像，记录镜像 digest。
2. 在新实例安装精确依赖并校验模型 manifest；不要复用其他 revision 的模型目录。
3. 先启动 vLLM 和网关，等待 `/health` 返回版本 `2.1.0` 与预期模型名。
4. 执行短音频、长音频、热词、错误契约和 CER 冒烟。
5. 接入层先小比例引流，观察 5xx、P95/P99、waiting requests、GPU 显存和取消/超时。
6. 达到观察窗口且无回归后逐步扩流；旧实例保持可回退，不立即删除模型或镜像。

## 8. 回滚流程

回滚是可逆的实例/流量切换，不对线上目录执行 `git reset --hard` 或覆盖模型文件：

1. 在 Gateway/LB 停止向 v2.1.0 新实例继续扩流，并将流量切回上一已验收镜像。
2. 确认上一实例 `/health`、单条转写和关键指标正常后，再摘除异常实例。
3. 若仅配置回滚，使用上一版本完整环境变量集重建实例，避免混用新旧参数。
4. 若模型 revision 回滚，使用上一 revision 对应的独立模型目录和 manifest；禁止在原目录覆盖。
5. 保存故障时的 vLLM/网关日志、指标、请求 ID、模型 manifest 和镜像 digest用于复盘。
6. 修复后重新执行本文件全部门禁，通过新 tag/镜像再次发布，不在原 tag 上覆盖。

## 10. 架构级候选 Aligner 验收

当前主服务已经固定 `vllm[audio]==0.19.1`，并在同一 Python 环境暂保 Transformers 4.57.6
与 `qwen-asr==0.0.6` PyTorch ForcedAligner。本节的 `PERF-ARCH-001` 仅验收后续
vLLM token-classify Aligner，`PERF-ARCH-002` 仅验收条件触发的 TensorRT 路线；两者都不表示
当前时间戳链路已迁移。所有模型只读取 ModelScope 固定 revision 本地目录，运行期不得使用
Hugging Face 下载链路。

### 10.0 主 ASR 0.19.1 前置门禁

在测试候选 Aligner 前必须先关闭两个时间戳开关，完成当前 vLLM 0.19.1 主 ASR 验收：

1. 同硬件、同 GPU、同主模型 revision、同音频 SHA256、同 API、同语种和同并发执行三轮
   ASR-only；成功率必须 100%，`Server-Timing` 覆盖率必须 100%。
2. 覆盖自动/显式语种、热词、multipart、10/30/90/300/2000 秒、Fast Tokenizer 并发稳定性、
   分片顺序、错误契约和全量 CER。
3. 相对冻结的 0.16 ASR-only 正式中位数，CER 不得退化，吞吐、P95/P99 和资源保护指标退化
   不得超过 5%；新版参数变化必须逐项单变量验证，不能为通过门禁降低并发或放宽检查。
4. 前置门禁未通过则回滚部署镜像且不继续 Aligner Phase A/B；通过只代表主 ASR 迁移完成，
   不能据此宣称 token-classify Aligner 已集成。

### 10.1 通用门禁

1. 同硬件、同 GPU 拓扑、同音频 SHA256、同文本/语言、同 batch 和同并发对照当前 PyTorch
   batch=32 候选；若使用额外 GPU，报告必须明确标记为拓扑/硬件收益。
2. 先测独立 Aligner 原始接口：相对当前 PyTorch 对照中位吞吐至少提升 30%；再接网关测默认
   时间戳链路：端到端 `audio_s/s` 至少提升 20%。两项均要求三轮可重复和 100% 成功率。
3. 逐样本比较对齐单元文本和数量；所有时间戳必须有限、严格单调、`start <= end` 且不越音频
   边界。不能用放宽边界、删除异常单元、回退中文或分片边界伪装成字/词级时间戳来通过。
4. 覆盖 ForcedAligner 11 种支持语言、自动/显式语种、10/30/90/300/2000 秒或最接近的可追溯
   样本、batch 1/8/16/32、低流量和并发 96；保存输入 manifest、依赖锁、镜像 digest、GPU、
   驱动/CUDA、完整命令和三轮 JSON。
5. 完成 `/chinese_asr` 字/词级与句级契约、部分不支持语种契约、全量 CER、混合时长分桶
   P95/P99、取消/超时、队列背压、候选服务不可达、重启和 SIGTERM 排空。不得自动重试可能已
   提交的 POST。
6. 候选失败或未达门禁时必须回滚到当前 `src/aligner.py` 路径；不能在同一请求中双跑后择优，
   也不能静默退回分片边界。

### 10.2 新版 vLLM token-classify 专项

- 启动日志和环境证据必须记录精确 vLLM 版本，不允许 `latest`；确认模型类型确为 Qwen3
  ForcedAligner token classification/pooling，而不是主 ASR 生成模型。
- 验证 `<timestamp>` token 位置的分类时间桶、`timestamp_segment_time` 换算和官方
  `parse_timestamp()` 结果；记录模型原始执行、排队、processor 与后处理耗时。
- 候选服务必须只读取本地 ModelScope 固定 revision；断网启动和推理应成功，缺失文件应明确
  启动失败。

### 10.3 TensorRT 专项

- 只有新版 vLLM spike 未达架构门禁且 forward 仍是主瓶颈时才开始；首轮只允许 FP16/BF16。
- 保存可复现导出脚本、ONNX/中间图 SHA256、TensorRT 版本、builder 参数、optimization profile
  和引擎 SHA256。profile 至少覆盖 batch 1/8/16/32、最长 32 秒音频及实际文本长度范围；超出
  profile 必须明确拒绝，不得返回截断或伪造结果。
- CPU 侧必须保留官方分词/`encode_timestamp()` 和 `parse_timestamp()` 语义，以及 timestamp
  mask、单调性和边界校验。FP16/BF16 通过全部质量门禁后，INT8 才能另立实验并准备代表性校准集。
