# 使用说明（dev，基于 v2.1.0）

## 1. 环境准备

目标平台为 Linux + NVIDIA CUDA。必须创建独立虚拟环境，不与 Paraformer、funasr、
TensorRT 或旧 Transformers 5.x 环境混装。

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-infer.txt
python -m pip install -r requirements-aligner.txt
python -m pip check
python -c "import vllm, transformers; print(vllm.__version__, transformers.__version__)"
```

锁定依赖为 `vllm[audio]==0.19.1`、`transformers==4.57.6`、`aiohttp==3.13.3`、
`soundfile==0.13.1`、`psutil==7.0.0` 和 `qwen-asr==0.0.6`。主 ASR 使用 vLLM 0.19.1，
ForcedAligner 仍使用 qwen-asr 0.0.6 PyTorch 后端；不要使用 `--no-deps`。

### GPU 驱动与 CUDA 约束

vLLM 0.20 及以上默认绑定 PyTorch 2.11 + CUDA 13.0，需要 580 及以上 NVIDIA 驱动。目标 A10
宿主驱动为 535，只支持 CUDA 12.x，因此本项目固定 0.19.1 并且必须使用 CUDA 12.9 的
`v0.19.1-x86_64` 基础镜像，不能使用 `-cu130` 变体。启动前会校验 PyTorch 为 CUDA 12.x 构建
并实际初始化 CUDA；不匹配时直接失败，不静默降级到 CPU。若之后宿主驱动升级到 580 以上，
可重新评估上调 vLLM，但必须重跑全部功能与性能门禁。

## 2. 模型准备

下载只使用 ModelScope 和 Python 标准库 `urllib`：

```bash
python scripts/download_model.py
```

默认主模型为 `Qwen/Qwen3-ASR-0.6B`，固定 revision
`4ce9cc728b473a5aedbe7b6e1ea45646316824dc`，目录为
`models/qwen3-asr-0.6b/vllm`。默认 Aligner 为 `Qwen/Qwen3-ForcedAligner-0.6B`，固定
revision `cf1c50164ea3ac48240d12bef5ead74aee0720cc`，目录为
`models/qwen3-forced-aligner-0.6b/pt`；`run.sh` 会检查并按需下载两者。下载器验证大小和
SHA256，支持 `.part` 原子替换、Linux 文件锁和 manifest。不要手工把其他 revision 覆盖到
同一目录。

## 3. 启动与停止

```bash
bash run.sh
```

脚本先检查端口和依赖、检查/下载模型，再启动 `127.0.0.1:8081` 的 vLLM；健康后启动
`0.0.0.0:8080` 的网关。客户端只访问 8080。任一进程退出时另一个会被清理；按 `Ctrl+C`
统一停止。`run_gateway.sh` 只用于后端已单独运行时调试。

`run.sh` 把 `src` 加入 `PYTHONPATH`，Python 启动时自动加载 `src/sitecustomize.py`。除固定
Transformers regex 兼容外，该文件还用进程级可重入锁保护 Fast Tokenizer 的完整公共调用。
该锁用于修复历史 vLLM 0.16.0 并发路径中的 `Already borrowed`；迁移到 0.19.1 后暂时保留，
不得在重跑并发稳定性和 CER 门禁前移除。并发 96 验收仍要求日志中
`RuntimeError: Already borrowed` 和 `upstream_status=400` 均为零。

```bash
curl http://127.0.0.1:8080/health
# {"status":"ok","version":"2.1.0","model":"qwen3-asr","timestamps":true,"aligner_device":"cuda:0"}
```

端口冲突：

```bash
ss -ltnp "sport = :8080"
ss -ltnp "sport = :8081"
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

确认旧进程后正常 `kill <PID>`，不要优先使用 `kill -9`。

### 分片级对齐流水（可选，默认关闭）

默认（批量模式）先等整条请求全部分片完成 ASR，再整体提交对齐，两个阶段完全串行。10 秒音频
只有一个分片，看不出差别；但 7500 秒上限对应约 235 个分片时，对齐要等最后一个分片识别完才
开始。开启 `ALIGNER_PIPELINE_ENABLED=true` 后，每个分片识别完成即提交对齐，两阶段重叠。

入队与跨请求合批语义完全不变，只是提交时机提前，因此单分片请求两种模式等价。

```bash
ALIGNER_PIPELINE_ENABLED=true bash run.sh
```

**指标语义变化。** 流水模式下 `aligner_latency_ms` 覆盖“首个分片提交到全部对齐完成”，与 ASR
时间部分重叠，不能与批量模式的同名字段直接相减比较。`aligner-queue` 取各分片排队等待的最坏
值而不是整条请求的单一等待值。日志与性能报告新增 `aligner_pipeline` 字段标明本次模式。

已验证语义：乱序完成的分片仍按原索引归位；空文本与不支持语种的跳过行为不变；同一分片重复
提交会显式报错；整批失败向调用方抛出且不残留未完成任务；请求取消只取消自身任务，不影响已
启动的共享 CUDA 批次。

### ForcedAligner 批大小

`ALIGNER_BATCH_SIZE` 默认为 32，来自目标 A10 实测：端到端由 107.33 升至 228.57 audio_s/s，
显存峰值约 20315 MiB。设为 1 可回退到逐片调用，此时吞吐约 107 audio_s/s，仅在排查问题或
显存受限时使用。放大到 48 已因收益不足 5%、显存再增被拒绝，不要继续加大。

### NVIDIA MPS

默认时间戳模式下 vLLM 与 Aligner 是同卡两个 CUDA 进程。无 MPS 时二者的 kernel 只能靠时间片
轮转，存在明显互等；走 MPS 后可并发执行。目标 A10 双向三轮实测：

| 指标 | 无 MPS | MPS | 变化 |
|---|---:|---:|---:|
| 吞吐 audio_s/s | 228.57 | 274.22 | +19.97% |
| 平均延迟 ms | 4133.8 | 3437.4 | -16.85% |
| P95 ms | 4470.3 | 3740.6 | -16.32% |
| 显存峰值 MiB | 20315 | 20532 | +217 |

代价是单请求 ASR 阶段上升约 28%，属于用单条延迟换整体吞吐。

**为什么需要主动管理。** MPS 是宿主级透明特性：只要控制守护进程在运行且管道目录可达，任何
CUDA 进程都会自动作为 MPS 客户端接入；未设置 `CUDA_MPS_PIPE_DIRECTORY` 时运行时仍会查默认
`/tmp/nvidia-mps`。所以单靠环境变量无法决定是否走 MPS。实测即使把开关设为 false，只要守护
进程在运行，两个进程仍以 `M+C` 方式接入。因此 `run.sh` 会主动把实际状态调整到与 `ENABLE_MPS`
一致：

| `ENABLE_MPS` | 守护进程状态 | `run.sh` 行为 |
|---|---|---|
| `true` | 不在线 | 启动守护进程，等待就绪；失败则拒绝启动 |
| `true` | 在线 | 直接复用 |
| `false` | 在线且无活跃客户端 | 停止守护进程，改用独立上下文 |
| `false` | 在线且有活跃客户端 | **拒绝启动**，不强行停止可能被他人共用的守护进程 |
| `false` | 不在线 | 正常启动 |

状态调整安排在端口等快速失败校验之后，避免因这些校验退出而遗留与配置不符的守护进程状态。
`quit` 在仍有客户端连接时会无限等待，因此停止操作带 30 秒超时兜底；缺少 `timeout` 命令时
直接拒绝启动，不做无超时的阻塞调用。

判定活跃客户端用的是"是否存在 MPS server"。server 由首个客户端接入时创建、在最后一个客户端
退出后消失，比解析 `get_device_client_list` 的非结构化输出可靠。

`run.sh` 退出时**不会**自动恢复守护进程状态，因为它可能被其他进程共用。

使用步骤。启用时可以直接交给 `run.sh`，也可以手工预先启动守护进程：

```bash
export CUDA_MPS_PIPE_DIRECTORY=/tmp/nvidia-mps
export CUDA_MPS_LOG_DIRECTORY=/tmp/nvidia-mps-log
mkdir -p $CUDA_MPS_PIPE_DIRECTORY $CUDA_MPS_LOG_DIRECTORY
nvidia-cuda-mps-control -d
```

容器必须以 `--ipc=host` 运行并挂载管道目录，Compose 用法见 `docker-compose.yml` 内注释。
然后在同一环境中启动服务，使两个进程都继承管道目录：

```bash
ENABLE_MPS=true bash run.sh
```

确认实际接入：`nvidia-smi` 进程列表中应出现 `nvidia-cuda-mps-server`，且 vLLM 与网关的
`Type` 为 `M+C`。

采集无 MPS 基线时反过来：

```bash
ENABLE_MPS=false bash run.sh
```

若守护进程仍有活跃客户端，本次启动会被拒绝，需要先停掉那些客户端。

**校验行为。** `ENABLE_MPS=true` 时，缺少 `nvidia-cuda-mps-control`、守护进程无法拉起，或
vLLM 就绪后仍未创建任何 MPS server，`run.sh` 都会直接退出。这是必要设计：实测守护进程缺失时
服务能正常启动、成功率与 `Server-Timing` 覆盖率均 100%，但吞吐会静默下降约 17.8%，没有任何
告警。宁可拒绝启动，也不允许带着与配置不符的状态运行。

第二道校验只判断 MPS server 是否存在。若 server 由其他进程创建而本次 vLLM 未接入，仍可能
误判通过，因此正式发布须人工核对 `Type` 为 `M+C`。

**故障影响。** 已实测：网关退出后 vLLM 存活且显存完整释放；网关可单独重启并挂回同一 server；
`quit` 会阻塞等待客户端断开，不打断在跑的服务；守护进程被强杀后 server 变孤儿继续服务，
时间戳与基准逐项一致。未发现进程连坐或结果失真。

**安全提示。** `--ipc=host` 会与宿主共享 IPC 命名空间，降低容器隔离性；MPS 客户端共享同一
CUDA 上下文，显存不再由各进程预算独立隔离。请按自身安全与容量要求评估后启用。

默认上限为 7500 秒、解码后音频 229 MiB、完整请求体 308 MiB。三项互相绑定，按目标输入格式
16 kHz 单声道 PCM16 WAV 推导：

```text
7500 s × 16000 Hz × 1 ch × 2 B = 240,000,000 B
加 44 B WAV 头            = 240,000,044 B ≈ 228.88 MiB → MAX_UPLOAD_MB=229
Base64 膨胀 4/3           ≈ 305.18 MiB，留 JSON 字段与热词开销 → MAX_JSON_BODY_MB=308
```

修改任一项都必须重算其余两项，否则会出现时长未到就被字节上限拒绝，或字节上限失去保护作用。
更高采样率、多声道或 24/32 位输入在 7500 秒下会先触发字节上限，属于预期拒绝。时长只有解析
音频后才能获知，两层字节限制仍负责在 HTTP 接收和解码阶段保护内存。

7500 秒按 32 秒分片会产生约 235 个物理分片，单请求墙钟、网关 RSS 和分片在途上限都会显著
高于此前的 2000 秒场景，必须在目标机重新验证内存峰值与尾延迟。

当前部署默认是 `CHUNK_CONCURRENCY=3`、`LONG_CHUNKS_IN_FLIGHT=96`，与历史 A10 纯 90 秒
最高吞吐组合一致；默认同卡 Aligner 和 0～2000 秒混合流量仍必须重新验证显存、吞吐和 P95/P99。

### 默认 ForcedAligner 时间戳

```bash
python -m pip install -r requirements-aligner.txt
python -m pip check
bash run.sh
```

`run.sh` 会仅从 ModelScope 下载 `Qwen/Qwen3-ForcedAligner-0.6B` 的固定 revision。Aligner
worker 从容量为 `ALIGNER_QUEUE_SIZE` 的有界物理分片队列取任务，从首条任务起最多等待
`ALIGNER_BATCH_WAIT_MS`，达到 `ALIGNER_BATCH_SIZE` 后立即调用官方批量 `align()`；批次可以
跨 `/chinese_asr` 请求，但结果始终按请求和原物理分片索引拆回。实验性预解码默认关闭；开启
`ALIGNER_PREDECODE_ENABLED` 后，会在 ASR 阶段使用 `ALIGNER_DECODE_WORKERS` 个 worker 提前
生成 PCM，并在入队前按 `ALIGNER_PREDECODE_MAX_MB` 预占全局字节预算。单片超过总预算时仍走
原批内解码；失败和取消释放预算，预解码错误不会静默降级。`ALIGNER_ATTENTION_BACKEND`
默认 `auto`，不会覆盖 Transformers 的自动选择；启动日志分别记录配置值和模型最终实际后端。
显式 `sdpa` 或 `flash_attention_2` 仅用于目标 GPU 单变量实验，依赖或模型不支持时启动失败，
不会回退其他后端。当前固定镜像未安装 `flash_attn`，因此显式 FA2 已阻塞；不要在运行容器内
临时安装依赖。启动脚本会在启动 vLLM 前给出明确错误。默认 batch=1 保留逐片行为，目标 A10 动态微批实验可从以下单 worker、batch=4 开始：

```bash
ALIGNER_CONCURRENCY=1 ALIGNER_BATCH_SIZE=4 \
ALIGNER_BATCH_WAIT_MS=5 ALIGNER_QUEUE_SIZE=256 bash run.sh
```

单 A10 同卡实际是 vLLM 与网关中的 Aligner 两个 CUDA 进程；ForcedAligner 只支持 Chinese、
English、Cantonese、French、German、Italian、Japanese、Korean、Portuguese、Russian、Spanish。
请求未传 `language` 时，主模型逐物理分片自动检测，并将检测标签直接用于对齐。支持的分片执行真实
对齐；语种为空或为 Malay、Arabic 等非上述 11 种语言的分片会显式跳过对齐，但不会中断
ASR：接口返回 HTTP 200，保留该分片的 `text`、`slid` 和物理边界，`words=[]`，顶层
`message` 列出跳过的分片与语种。服务不回退到 Chinese。

如果启用了句级时间戳但存在任一跳过分片，整条响应保留物理分片结构，顶层 `message` 同时
说明句级聚合已禁用；只有全部非空分片均成功对齐时才返回句级 `asr[]`。

若只需识别其他主模型语言而不需要真实字/词时间戳，可关闭两个开关后重启：

```bash
ENABLE_WORD_TIMESTAMP=false ENABLE_SENTENCE_TIMESTAMP=false bash run.sh
```

此时 ASR 正常返回，`slid` 仍是主模型逐片标签，`timestamp` 仅表示物理分片边界，`words=[]`。
默认同卡双模型必须用 `nvidia-smi` 检查峰值并验证 OOM、吞吐和 P95/P99。
`run_gateway.sh` 不安装依赖、不下载模型，只用于后端和权重已准备好的独立调试。

Compose 默认只拉取 `zhxgharbor.istarshine.com/asr/qwen3-asr-infer:0.19.1`，不执行本地构建：

```bash

```

`blinker==1.9.0`；不要删掉该步骤或跳过 `pip check`。

## 5. 结构化日志与 API 调用

网关请求协程只把 `LogRecord` 放入容量为 `LOG_QUEUE_SIZE` 的内存队列，独立监听线程负责
格式化并写 stdout 和可选文件，避免慢磁盘或容器 stdout 背压直接阻塞 aiohttp 事件循环。文件
固定为 `LOG_DIR/gateway.log`，达到 `LOG_MAX_FILE_MB` 后按 `.1`、`.2` 等滚动，最多保留
`LOG_BACKUP_COUNT` 份；启动时还会清理超过 `LOG_RETENTION_DAYS` 天的备份及旧版
`gateway_<pid>.log*`。因此文件日志同时受大小、份数和时间约束，跨进程重启仍能清理。

Compose 使用命名卷 `asr-logs` 持久化文件日志；`docker compose down` 默认保留该卷，只有
`docker compose down -v` 才删除。`run.sh` 保留容器 stdout 专门输出网关 JSON，并把启动提示、
下载器和 vLLM 文本统一送到 stderr；Docker 日志记录保留 `stdout/stderr` 来源，虽然
`docker compose logs` 默认会合并展示。Compose 的 `json-file` 驱动默认按
`DOCKER_LOG_MAX_SIZE=100m`、`DOCKER_LOG_MAX_FILES=5` 对两条流统一实施容器级轮转，不受应用
日志参数控制。

`aligner_completed` 和请求完成日志额外记录 `aligner_batch_count`、
`aligner_batch_size_max/mean` 与 `aligner_queue_depth_max`，用于证明实际跨请求合批和观察背压；
还记录 `aligner_batch_audio_decode_ms`、`aligner_batch_model_call_ms`、
`aligner_batch_result_build_ms`，分别表示请求参与的唯一共享批次内联 WAV 解码、官方
`model.align()` 完整调用和结果构建耗时之和。预解码实验另记录 `aligner_predecode_wait_ms`、
`aligner_predecode_audio_decode_ms` 和 `aligner_predecode_count`；前者是进入 Aligner 后等待已提交
预解码完成的残余墙钟，后两者是该请求预解码 CPU 耗时之和与命中分片数。它们是批次或请求级
诊断成本，不是可与请求 `total` 直接相加的独占耗时，也不进入固定 14 项 `Server-Timing` 或
业务响应。队列满或 PCM 预算不足时请求等待可用容量，不会无限增加已解码数据。

每条网关日志包含 `timestamp`、`level`、`logger`、`event`、`message`、`request_id`。请求完成
事件保留 `input_fields`、`output_fields`、HTTP 状态、结果分类、总耗时以及音频大小/时长、
分片数、语言模式和结果字符数等统计摘要；`/chinese_asr` 还包含结构化 `input_json` 和
`result_json`。`input_json.base64` 仅保留前 64 个 ASCII 字节，完整 Base64 长度由
`base64_encoded_chars` 记录；成功和业务错误响应都会写入 `result_json`。业务 JSON 仍受日志
字符串、集合和嵌套上限约束，超限项会明确标记截断。取消或断连使用观测状态 `499`。4xx/5xx
记录业务错误码或异常类型，代理端点额外记录上游状态和响应字节数。`DEBUG` 级别记录后端逐
分片耗时，并记录成功的健康检查/指标/模型列表请求；默认 `INFO` 不保存这些高频管理端点的
成功访问。

队列满时请求不会等待日志 I/O；被丢弃的数量会附加在下一条成功日志的
`dropped_logs_before`，进程关闭时仍未上报的数量写入 `log_records_dropped_on_shutdown`。文件或
stdout 写入失败后，对应 handler 会被停用并输出不含业务字段的固定内部错误事件，避免反复打印
logging traceback。正常退出会先排空队列再关闭文件。

日志会记录 `/chinese_asr` 的热词、`article_url`、语言和识别结果等业务内容；输入音频
Base64 只保留前 64 字节，不记录其余 Base64 或解码后的音频二进制。multipart 文件名和后端
Prompt 也不落日志。必须把 stdout、日志采集系统和命名卷按敏感数据管理，限制访问权限，并按
业务要求设置 `LOG_RETENTION_DAYS`。现有字段名、音频大小/时长、分片、语言、结果计数、
错误码、状态和耗时等统计摘要仍全部保留。定位问题时使用响应头 `X-Request-ID` 查询：

```bash
docker compose logs qwen3-asr | grep '<request-id>'
docker compose exec qwen3-asr grep '<request-id>' /var/log/qwen3-asr/gateway.log*
```

完整字段、成功/失败样例、错误码和响应头见 [API 文档](API文档.md)。

```bash
AUDIO_BASE64="$(base64 -w 0 test_data/audio_16000_10s.wav)"
curl http://127.0.0.1:8080/chinese_asr \
  -H 'Content-Type: application/json' \
  -d "{\"base64\":\"$AUDIO_BASE64\",\"article_url\":\"source-001\",\"hotwords\":[\"通义千问\"]}"

curl http://127.0.0.1:8080/v1/audio/transcriptions \

```

## 6. 测试与 CER

```bash
python tests/test_chinese_asr_single.py --audio test_data/audio_16000_10s.wav
python tests/test_service.py --api-mode chinese-asr \
  --audio test_data/audio_16000_30s.wav --concurrency 96 --total 2000 \
  --require-server-timing \
  --output-json performance-results/PERF-BASE-001-run-01.json
python tests/verify_qwen_single.py --api-mode chinese-asr \
  --input test_data --ref test_data --baseline-cer 0.05
```

压测器继续输出终端摘要，并可通过 `--output-json` 原子写入 `schema_version=1` 的严格 JSON。
报告包含 Git/运行环境、白名单性能变量、音频文件名/大小/SHA256/时长、测试参数、成功失败、
QPS、分片 RPS、audio_s/s、端到端及各阶段分位数、`Server-Timing` 覆盖率、GPU/CPU 采样，
以及正式测试前后的 vLLM Prometheus 非 bucket 数值样本。报告不保存音频内容、热词值、
`article_url` 值或任意非白名单环境变量；文件名和内部服务 URL 仍应按部署信息管理。

`--require-server-timing` 会把成功响应缺少、重复或包含非法阶段计时视为测试失败，建立正式基线
时必须开启。`--metrics-url` 默认是 `http://127.0.0.1:8080/metrics`；抓取失败会写入报告但不
中断业务压测，明确不需要指标时使用 `--skip-metrics`。分片队列和 `asr-backend` 是每请求的
分片累计值，`asr` 和 `total` 才是墙钟耗时，两类数值不得相加。

CER 门禁要求参考覆盖 `--limit` 处理后的全部输入，且每条参考经 NFKC、去空白后非空；缺失、
空参考或零计分样本均非零退出。目录参考使用同名 `.txt`；单文件参考用 `.txt`；JSONL 每行
包含字符串 `wav`、`text`，相对音频路径以 JSONL 所在目录解析；直接文本使用 `--ref-text`。

## 7. 排障

- Docker 构建在 `pip check` 报 `pygobject ... requires pycairo`：这是私有 vLLM 基础镜像预装
  PyGObject 但缺少系统依赖；Dockerfile 已安装 `python3-cairo`，不应删除或忽略 `pip check`。
- Docker 构建提示 `/bin/sh: python: not found`：部分 vLLM 基础镜像只提供 `python3` 或
  `python3.12`；当前 Dockerfile 会自动探测解释器并创建 `/usr/local/bin/python` 兼容入口。
  请确认使用最新 Dockerfile 后以 `--no-cache` 重新构建。
- `qwen3_asr` 模块缺失：确认 vLLM 为 0.19.1，并使用全新环境重新安装
  `requirements-infer.txt`；不要混用其他 vLLM 版本残留文件。
- `The NVIDIA driver on your system is too old`：镜像内 PyTorch 为 cu130 构建而宿主驱动低于
  580。改用 CUDA 12.9 基础镜像重建，或升级宿主驱动；不要在容器内安装 CUDA Toolkit 绕过。
- Transformers 冲突：确认版本为 4.57.6，不使用 `--no-deps`。
- 模型 manifest 身份不一致：为新 revision 使用新的 `VLLM_MODEL_DIR`，不要覆盖旧目录。
- 网关 502：检查 `curl http://127.0.0.1:8081/health` 及 vLLM 日志。
- 网关 503：后端过载；降低入口并发或扩容，不要无限增加队列。
- 网关 504：分片推理超过 `BACKEND_TIMEOUT`；先查后端等待队列和 GPU 状态。
- MP3/M4A 无法解码：系统 libsndfile 可能未启用对应格式，生产优先 WAV/FLAC/OGG。
- 时间戳启动失败：安装 `requirements-aligner.txt`，执行 `python -m pip check`，并检查 Aligner manifest。
- 时间戳响应 `message` 提示跳过分片：对应 `slid` 不在 Aligner 的 11 语种内；ASR 未失败，
  该分片 `words=[]` 且 `timestamp` 仅为物理边界。需要完整真实对齐时应使用受支持语种音频；
  不得用错误语种强制对齐。
- 单卡时间戳 OOM：降低显式 `VLLM_GPU_MEMORY_UTILIZATION`，或将 Aligner 移至独立 GPU/CPU。

完整上线和回滚步骤见 [发布验收](发布验收.md)。
